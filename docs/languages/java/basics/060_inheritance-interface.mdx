# 継承とインタフェース

このページでは、クラスの継承、インタフェース、オーバーライド、そして「宣言上の型」と「実行時の型」の違いを押さえます。  
ポリモーフィズムの入口です。

## なぜ型の関係が必要か

注文処理にも、キャンセルにも、共通の「実行して結果を残す」流れがある。  
同じ手続きをコピペで増やすと、仕様変更のたびに漏れが出ます。  
共通部分を親やインタフェースに寄せ、差分だけを差し替える、というのが継承・実装のうれしい点です。

## 継承（extends）

子クラスは親クラスのフィールドやメソッドを引き継ぎ、必要なら振る舞いを差し替えます。  
Java のクラス継承は **単一継承**（親はひとつ）です。

```java
class Task {
    void complete() {
        System.out.println("task done");
    }
}

class UrgentTask extends Task {
    @Override
    void complete() {
        System.out.println("urgent task done");
    }
}
```

`@Override` は必須ではありませんが、付けておくとシグネチャの食い違いをコンパイル時に検知できます。

## インタフェース（implements）

インタフェースは「できること」の契約です。  
クラスは複数のインタフェースを実装できます。

```java
interface Notifiable {
    void notifyUser(String message);
}

class MailNotifier implements Notifiable {
    @Override
    public void notifyUser(String message) {
        System.out.println("mail: " + message);
    }
}
```

「共通の親クラスに無理にまとめない方が自然」なとき、インタフェースの方がすっきりすることが多いです。  
実装の詳細はクラス側に残し、呼び出し側はインタフェースだけに依存できます。

## 参照型と実行時の型

変数の型（コンパイル時に見える型）と、実際に入っているオブジェクトの型は一致するとは限りません。

```java
Task task = new UrgentTask();
task.complete(); // "urgent task done"
```

- **参照型（宣言型）**: `Task` … 呼べるメンバーの上限を決める
- **実行時の型**: `UrgentTask` … 実際に動くオーバーライド先

呼び出し側は `Task` として扱いつつ、実行時には子の実装が選ばれます。  
これがポリモーフィズムの基本動作です。

:::tip[覚えておくこと]

呼べるかは参照型、どの実装が動くかは実行時の型。  
オーバーライドされたインスタンスメソッドは、実行時の型で解決される。

:::

## キャストの注意

どうしても子固有のメソッドを呼びたいとき、キャストします。  
型が合わないと実行時に `ClassCastException` です。

```java
Task task = new Task();
UrgentTask urgent = (UrgentTask) task; // 失敗しうる
```

現代の Java では、パターンマッチングで安全に分岐できます。

```java
if (task instanceof UrgentTask urgent) {
    // urgent として使える
}
```

キャストが増える設計は、そもそも参照型の選び方が粗いサインかもしれません。  
インタフェースや適切な抽象に寄せられないか、先に考えます。

似た単語なので、レビューコメントではどちらを指すか明示すると誤解が減ります。

## よくあるつまずき

- 親の参照で子専用メソッドを呼ぼうとしてコンパイルエラーになる
- キャストして動いたコードが、別の実装クラスに差し替わった瞬間に落ちる
- 継承階層を深くしすぎて、変更の影響範囲が見えなくなる

## まとめ / 次に学ぶとよいこと

- 継承は実装の再利用と差し替え、インタフェースは契約の共有
- 参照型が API の上限、実行時型が実際の振る舞い
- キャストは最後の手段に近い
