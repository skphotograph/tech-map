# static と final

`static final` と並んでいるのを見て、「全部まとめて定数」と思ってしまうことがあります。  
実際は役割が違います。  
**static は所属の話、final は再代入の話** です。

共有ホワイトボードと、「この席は予約済みで付け替え禁止」の札——似て見えるけど、固定しているものが違います。  
このページでは、定数の置き方と、「インスタンスなしで呼べるメソッド」の意味を整理します。

`static` は「クラスに属する」共有の書き方です。  
ここでは書き方・定数・`this` が使えない制約に集中します。

## なぜこの二つが紛らわしいか

コード上ではよく隣同士に出てきます。  
だから混同しやすいだけです。  
「クラス全体で一つ」と「一度入れたら付け替えない」は、別々に覚えます。

## static フィールド：クラスに一つ

インスタンスフィールドは、オブジェクトごとに別の値を持てます。  
`static` フィールドはクラスに紐づき、**共有** されます。  
各自のノートではなく、会議室の共有ホワイトボードです。

```java
class OrderBoard {
    static int openCount = 0; // ボード全体で共有
    String orderId;           // 各ボードごと
}
```

```java
OrderBoard a = new OrderBoard();
OrderBoard b = new OrderBoard();
OrderBoard.openCount++;
System.out.println(b.openCount); // 同じ場所を見ている
```

カウンタやキャッシュ、設定の置き場として便利な一方、テストやマルチスレッドでは副作用の温床にもなります。  
「本当に全体で一つでよいか」を疑う癖が大事です。

```java
static List<byte[]> cache = new ArrayList<>();
```

このようなフィールドは、プロセスが生きているあいだ参照を持ち続けます。  
参照が残っているあいだは、消えたことになりません。

<details>
<summary>クラス定義の置き場（メタスペース）</summary>

クラスを初めて使うとき、JVM はクラスの定義情報をロードします。  
JDK 8 以降、クラスのメタデータは **メタスペース（Metaspace）** 側で管理されます。  
クラス定義と、各インスタンスの実データは別物です。  
`static` フィールドの値は「各インスタンスにコピーされるもの」ではありません。

</details>

## static メソッド：インスタンスなしで呼ぶ

`static` メソッドは、インスタンスを用意せずにクラス名で呼びます。  
ユーティリティやファクトリの入口によく使います。

```java
class OrderIds {
    static String prefix(String raw) {
        return "ORD-" + raw;
    }
}

// 呼び出し
String id = OrderIds.prefix("1001");
```

制約として、**同じクラスのインスタンスフィールドやインスタンスメソッドには、呼び出す側のオブジェクト（`this`）なしでは触れません**。  
`static` メソッドの中には `this` が無いからです。  
共有ホワイトボード側の手順からは、誰かの個人ノートを勝手に読めない、と考えれば足ります。

```java
class User {
    String name;

    static void printName() {
        // System.out.println(name); // コンパイルエラー
    }
}
```

ユーティリティや、生成結果を返すファクトリ（「クラス名から作る入口」）によく使います。  
インスタンスの状態を触りたい処理は、最初からインスタンスメソッドにした方があとで楽なことが多いです。

:::tip[覚えておくこと]

static は「インスタンスに属さない」。  
共有状態を持つなら、寿命とテスト容易性を意識する。

:::

## final：再代入できない

`final` は、変数への **再代入を禁止** します。  
「この席に座る人（参照）は付け替えない」予約札です。

```java
final int maxRetry = 3;
// maxRetry = 5; // コンパイルエラー

class User {
    String name;
}

final User user = new User();
user.name = "b"; // 中身の変更は可能（参照の付け替えだけ不可）
// user = new User(); // コンパイルエラー
```

参照型の `final` は「中身が不変」を意味しません。  
席の予約は固定でも、座っている人のノートの中身はまだ書けます。  
不変にしたいなら、フィールドを `final` にし、セッターを置かない、コレクションを変更不可にする、などが別途必要です。

## 定数の定番パターン

名前付きの定数は、よく次の形にします。  
壁に貼った「状態名のプレート」を、みんなで同じ表記で読むイメージです。

```java
public final class OrderStatus {
    public static final String OPEN = "OPEN";
    public static final String PAID = "PAID";
    public static final String SHIPPED = "SHIPPED";
    public static final String CANCELLED = "CANCELLED";

    private OrderStatus() {
        // インスタンス化させない
    }
}
```

- `static` … クラスから直接使う
- `final` … 参照を付け替えない
- 大文字スネークケース … 定数だと分かる命名慣習

数値リテラルや文字列リテラルがコード中に散らかるより、名前が付いている方が意図が残ります。

<details>
<summary>enum との使い分け（入口）</summary>

取りうる値が閉じた集合なら、`String` 定数より `enum` の方が型安全です。  
ここでは「定数の形」として `static final` を先に覚え、列挙型は設計の入口で深掘りします。

</details>

## よくあるつまずき

- `final` なリストの要素を `add` して「不変じゃなかった」と驚く（参照が final なだけ）
- static フィールドにリクエスト固有の情報を入れて、別ユーザーの値と混ざる
- インスタンスメソッドにすべき処理を static にし、あとから状態を持てなくなる

## まとめ / 次に学ぶとよいこと

- static は共有とインスタンス不要の呼び出し
- final は再代入禁止（オブジェクト不変とは限らない）
- 定数は `static final` ＋ 分かりやすい名前
