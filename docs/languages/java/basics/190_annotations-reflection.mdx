# アノテーションとリフレクション

コードにアノテーションを付けるだけで、検証やルーティングが動くフレームワークがあります。  
これはアノテーション自体が処理を実行しているのではなく、別のコードがメタデータを読み取り、規則に沿って動作しているためです。

## このページで分かること

- アノテーションが表すもの
- `Retention` と `Target` の役割
- リフレクションで型情報を調べる基本
- フレームワークが両者を使う理由と注意点

## アノテーションはコードに付けるメタデータ

アノテーションは、クラス、メソッド、フィールドなどに付加する情報です。  
コンパイラー、ビルドツール、実行時のフレームワークが読み取って利用します。

```java
@Override
public String toString() {
    return "Order";
}
```

`@Override` は、メソッドが基底型のメソッドをオーバーライドしている意図をコンパイラーへ伝えます。  
綴りや引数を間違えてオーバーライドできていなければ、コンパイルエラーになります。

## 独自アノテーションを定義する

```java
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
public @interface Handler {
    String value();
}
```

```java
@Handler("order")
final class OrderHandler {
}
```

`@Target` は、アノテーションを付けられる場所を制限します。  
`@Retention` は、アノテーション情報をいつまで保持するかを指定します。

| RetentionPolicy | 保持範囲           | 主な用途                     |
| --------------- | ------------------ | ---------------------------- |
| `SOURCE`        | ソースコードまで   | コンパイル時の検査補助       |
| `CLASS`         | class ファイルまで | バイトコード処理             |
| `RUNTIME`       | 実行時まで         | リフレクションによる読み取り |

:::tip[アノテーションは宣言だけ]

独自アノテーションを付けただけでは処理は起きません。  
読み取って動作するコンパイラー、ライブラリ、またはアプリケーションコードが必要です。

:::

## リフレクションで型を調べる

リフレクションは、実行時にクラス、メソッド、フィールドなどの情報を調べ、操作する仕組みです。

```java
Class<OrderHandler> type = OrderHandler.class;
Handler handler = type.getAnnotation(Handler.class);

if (handler != null) {
    System.out.println(handler.value());
}
```

実行結果:

```text
order
```

メソッド一覧も取得できます。

```java
for (Method method : type.getDeclaredMethods()) {
    System.out.println(method.getName());
}
```

## フレームワークが使う理由

フレームワークは、特定のアノテーションが付いた型を探し、登録や設定を組み立てることがあります。  
これにより、利用者は共通の登録コードを毎回書かず、宣言的に意図を示せます。

一方で、呼び出し関係が通常のメソッド呼び出しとして現れないため、動作を追いにくくなることがあります。  
「誰が、いつ、どの範囲を探索し、何を登録するか」をフレームワークの仕様やログで確認することが重要です。

## リフレクションの注意点

- コンパイル時に検出できたはずの誤りが、実行時エラーになる場合がある
- private メンバーへの強い依存は、カプセル化や将来の変更を妨げる
- モジュール境界や実行環境の制約でアクセスできない場合がある
- 反射的な呼び出しは通常の呼び出しより追跡しにくい
- 外部入力から任意のクラス名やメソッド名を受け取る設計は、安全性を慎重に検討する必要がある

:::warning[アクセス制御を迂回しない]

`setAccessible` などで非公開メンバーへ無理にアクセスする設計は、Java のバージョンやモジュール設定で壊れやすくなります。  
公開 API、明示的な登録、サービスプロバイダー機構などを先に検討します。

:::

<details>
<summary>実行時リフレクション以外の方法</summary>

アノテーションプロセッサーは、コンパイル時にソース上のアノテーションを読み取り、コード生成や検査を行えます。  
起動時の探索コストや実行時エラーを減らせる場合がありますが、ビルド設定と生成物の理解が必要です。  
用途に応じて、実行時の柔軟性とコンパイル時の検査を選びます。
</details>

## よくあるつまずき

- `RetentionPolicy.RUNTIME` がないアノテーションを実行時に探す
- アノテーションを付ければ自動的に処理されると思い込む
- フィールド名やメソッド名を文字列で多用し、リファクタリングに弱くする
- リフレクションで例外を包み込み、根本原因をログから失う

## まとめ

- アノテーションは、コードへ意図や設定を付けるメタデータである
- 実行時に読むには、保持方針を `RUNTIME` にする
- リフレクションは柔軟だが、型安全性、追跡性、アクセス境界に注意する
- フレームワークの動作は、アノテーションを読む主体とタイミングから考える
