# 継承とインタフェース

注文の受付にも、お急ぎ便にも、共通の「確定して結果を残す」流れがある。  
同じ手続きをコピペで増やすと、仕様変更のたびに漏れが出ます。  
共通部分を親やインタフェースに寄せ、差分だけを差し替える——職種ごとのマニュアルを、共通編と専門編に分ける感覚です。

このページでは、クラスの継承、インタフェース、オーバーライド、`protected`、そして「宣言上の型」と「実行時の型」の違いを押さえます。  
ポリモーフィズムの入口です。

## なぜ型の関係が必要か

呼び出し側は「注文を確定する」とだけ知りたいことが多いです。  
中身が通常注文かお急ぎ便かは、差し替えられれば十分、という場面が増えます。  
共通の呼び方を守りつつ、実体ごとの振る舞いを変えられるのが、継承・実装のうれしい点です。

## 継承（extends）

子クラスは親クラスのフィールドやメソッドを引き継ぎ、必要なら振る舞いを差し替えます。  
Java のクラス継承は **単一継承**（親はひとつ）です。

```java
class Order {
    void confirm() {
        System.out.println("order confirmed");
    }
}

class ExpressOrder extends Order {
    @Override
    void confirm() {
        System.out.println("express order confirmed");
    }
}
```

`@Override` は必須ではありませんが、付けておくと **シグネチャ**（メソッド名と引数の型の並び）の食い違いをコンパイル時に検知できます。

## 親のコンストラクタを呼ぶ（`super`）

子を `new` するとき、親側の初期化も必要になることがあります。  
子のコンストラクタから、親のコンストラクタを呼ぶのが `super(...)` です。

```java
class Order {
    String orderId;

    Order(String orderId) {
        this.orderId = orderId;
    }
}

class ExpressOrder extends Order {
    ExpressOrder(String orderId) {
        super(orderId); // 親の Order(String) を先に実行する
    }
}
```

- `super(orderId)` は、親クラスのコンストラクタを呼び出す
- 親に「引数付きコンストラクタだけ」があるとき、子側で `super(...)` が要ることが多い

## `protected`: 子からも触れる見える範囲

[アクセス修飾子](./access-modifiers) では `public` / `private` / 修飾子なしを見ました。  
継承ではもうひとつ、`protected` がよく出ます。

| 修飾子      | ざっくりした意味                                       |
| ----------- | ------------------------------------------------------ |
| `protected` | 同じパッケージに加え、**別パッケージの子クラス**からも |

```java
public class Order {
    protected String orderId;

    public Order(String orderId) {
        this.orderId = orderId;
    }
}

public class ExpressOrder extends Order {
    public ExpressOrder(String orderId) {
        super(orderId);
    }

    public String shippingLabel() {
        return "[EXPRESS] " + orderId; // 子から protected フィールドを読める
    }
}
```

`private` だと子からも見えません。  
「親子で共有したいが、無関係なクラスには見せたくない」ときに `protected` を検討します。  
まずは `private` を基本にし、本当に子が要るときだけ開ける、で十分なことが多いです。

## インタフェース（implements）

インタフェースは「できること」の契約です。  
求人票の「必須スキル」に近く、抽象メソッドには本体（`{ ... }`）が無く、実装クラス側で中身を書きます。  
クラスは複数のインタフェースを実装できます。

```java
interface Notifiable {
    void notifyUser(String message);
}

class MailNotifier implements Notifiable {
    @Override
    public void notifyUser(String message) {
        System.out.println("mail: " + message);
    }
}
```

「共通の親クラスに無理にまとめない方が自然」なとき、インタフェースの方がすっきりすることが多いです。  
実装の詳細はクラス側に残し、呼び出し側はインタフェースだけに依存できます。

## 参照型と実行時の型

変数の型（コンパイル時に見える型）と、実際に入っているオブジェクトの型は一致するとは限りません。  
窓口の受付票は「注文」、対応する係員は「お急ぎ便チーム」——聞けることは受付票、実際の返事は係員、です。

```java
Order order = new ExpressOrder("ORD-1001");
order.confirm(); // "express order confirmed"
```

- **参照型（宣言型）**: `Order` … 呼べるメンバーの上限を決める
- **実行時の型**: `ExpressOrder` … 実際に動くオーバーライド先

呼び出し側は `Order` として扱いつつ、実行時には子の実装が選ばれます。  
これがポリモーフィズムの基本動作です。

:::tip[覚えておくこと]

呼べるかは参照型、どの実装が動くかは実行時の型。  
オーバーライドされたインスタンスメソッドは、実行時の型で解決される。

:::

## キャストの注意

どうしても子固有のメソッドを呼びたいとき、**キャスト**（「この参照を、別の型として扱う」宣言）をします。  
実行時の実体がその型でなければ `ClassCastException` です。

```java
Order order = new Order("ORD-1002");
ExpressOrder express = (ExpressOrder) order; // 失敗しうる
```

<details>
<summary>パターンマッチで安全に分岐する（Java 16+）</summary>

現代の Java では、`instanceof` と変数宣言をまとめて書けます。

```java
if (order instanceof ExpressOrder express) {
    // express として使える
}
```

</details>

キャストが増える設計は、そもそも参照型の選び方が粗いサインかもしれません。  
インタフェースや適切な抽象に寄せられないか、先に考えます。

## よくあるつまずき

- 親の参照で子専用メソッドを呼ぼうとしてコンパイルエラーになる
- キャストして動いたコードが、別の実装クラスに差し替わった瞬間に落ちる
- 継承階層を深くしすぎて、変更の影響範囲が見えなくなる

## まとめ / 次に学ぶとよいこと

- 継承は実装の再利用と差し替え、インタフェースは契約の共有
- 参照型が API の上限、実行時型が実際の振る舞い
- `protected` は子からも触れる見える範囲
- キャストは最後の手段に近い
