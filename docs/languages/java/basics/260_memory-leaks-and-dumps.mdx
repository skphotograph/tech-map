# メモリリークとヒープダンプ

Java の「メモリリーク」は、C 言語のように `free` し忘れた穴ではありません。  
**GC ルートから到達できるまま、もう使わないオブジェクトが残り続ける** 状態です。

[ヒープとガベージコレクション](./heap-and-gc) で到達可能性を、[終了・デッドロック・ThreadLocal](./shutdown-deadlock-threadlocal) でプールの止め方や `ThreadLocal` を見たあとに読むと、典型パターンが追いやすいです。  
このページでは、よくある保持の形と、ヒープダンプで「誰が照らしているか」を特定する流れを扱います。

## このページで分かること

- リークに見えるものと、単発のスパイクの違い
- 参照が切れない典型パターン
- ヒープダンプの取り方と、Histogram / Dominator / GC Roots の読み方
- 本番でダンプを取るときの注意
- ヒープ以外が増えるときの切り分け

## 増え方が違えば原因も違う

監視グラフを見て、次を区別します。

| 見え方                                                 | よくある中身                                     |
| ------------------------------------------------------ | ------------------------------------------------ |
| リクエストの山に合わせて上下し、GC 後に戻る            | 一時オブジェクトの量産。リークではないことが多い |
| GC しても戻らず、時間とともに上限へ近づく              | 参照の保持。リークっぽい状態                     |
| デプロイやホットリロードのたびに一段上がり、下がらない | クラスローダーやキャッシュの残留                 |
| ヒープ使用率は低いのに OS メモリだけ増える             | ネイティブ、直接バッファ、スレッドスタックなど   |

「メモリ使用量が増えた」だけではリークと断定しません。  
**回収後に戻るか、上限へ向かって単調に増えるか** が最初の分岐です。

:::tip[見る順番]

残っているインスタンスのクラス名より先に、それを保持している参照元を見ます。  
`Order` が 100 万件あっても、悪いのは `Order` そのものではなく、マップやキューかもしれない、という視点です。

:::

## 到達できるから残る、という再確認

[ヒープとガベージコレクション](./heap-and-gc) の到達可能性が、そのまま診断の定義です。  
暗い倉庫で、入口の灯りからケーブルをたどって届く棚だけが見える——届くかぎり、掃除は片付けてくれません。

```text
GC Root
  -> static な Map
      -> sessionId
          -> UserSession
              -> 大きなバイト配列
```

このとき Histogram で目立つのはバイト配列かもしれません。  
しかし切るべきなのは、多くの場合 **マップのエントリ寿命** です。  
「大きいものを消す」のではなく、「なぜルートから届くのか」を潰します。

## 切れない参照の典型

パターンは繰り返し出ます。  
コードレビューでも、ダンプでも、同じ名前が並びます。

### `static` なコレクションとプロセス寿命のキャッシュ

```java
class ReportCache {
    private static final Map<String, byte[]> pdfs = new HashMap<>();

    static void put(String key, byte[] pdf) {
        pdfs.put(key, pdf);
    }
}
```

キーを消す経路が無い、上限が無い、エントリの期限が無い、のいずれか（多くは全部）だと、プロセスが生きているかぎり増え続けます。  
「次のリクエストで使うかもしれない」は、無制限キャッシュの理由になりません。

上限付きのキャッシュ、明示的な無効化、外部のキャッシュ基盤、といった寿命設計が先です。  
`static` である必要がなければ、インスタンスの寿命に載せる方が切れやすいです。

### 登録したきり外さないリスナー

GUI に限りません。  
ドメインイベント、メッセージ購読、JMX、メトリクス、アプリケーションサーバのライフサイクルフックでも起きます。

```java
// イメージ: バスに「出荷時コールバック」を登録したきり
bus.subscribe(listener);
```

購読側オブジェクトがバスに強参照で残ると、画面やリクエストが終わってもグラフ全体が生きます。  
登録したら解除する、弱参照で登録する、購読の寿命をスコープと一致させる、のいずれかが必要です。

### `ThreadLocal` の置きっぱなし

スレッドプールでは、スレッドがリクエストをまたいで再利用されます。  
[終了・デッドロック・ThreadLocal](./shutdown-deadlock-threadlocal) で触れたように、`ThreadLocal` はスレッドごとに値を持つ道具です。

```java
private static final ThreadLocal<RequestContext> CONTEXT = new ThreadLocal<>();

void begin(RequestContext ctx) {
    CONTEXT.set(ctx);
}
```

`remove()` しないと、次のリクエスト、あるいはプール上のアイドルスレッドに、前の文脈が残ります。  
大きなオブジェクトを載せると、リークに加え、別ユーザーのデータを見せる事故にもなります。

```java
try {
    CONTEXT.set(ctx);
    handle();
} finally {
    CONTEXT.remove();
}
```

フレームワークが用意するリクエストスコープがあるなら、自前の `ThreadLocal` を増やさない方が安全です。

### 終わらないタスクとキュー

[並行処理](./concurrency) のプールや `Future` でも、同じ「参照が切れない」形が起きます。  
投げた仕事やキューに載った作業セットがルート側に残る、と捉えてください。

`ExecutorService` に投げた仕事が終わらない、拒否されず無制限キューに積まれる、キャンセルされない `Future` が結果を保持する、といった形でもグラフが残ります。

```java
executor.submit(() -> loadAllOrdersIntoMemory());
```

終了しないタスクは、スタックもヒープ上の作業セットもルート側に残します。  
停止時に `shutdown` しないプールは、プロセス終了を遅らせるだけでなく、保持するタスクグラフも残します。

### セッションや会話状態の消し忘れ

ログインセッション、ウィザードの途中状態、アップロード中の一時ファイルのバイト配列を、マップに ID で載せたまま期限切れにしない、は Web アプリで頻出です。  
件数 × 1 件あたりのグラフサイズを見積もると、上限の必要性が具体になります。

### クラスローダーが残る再デプロイ

アプリケーションサーバで WAR を載せ替えるとき、古いクラスローダーが誰かから参照されていると、そのローダーがロードしたクラスも static もアンロードされません。  
症状はヒープだけでなく **メタスペースの単調増加** としても出ます。  
保持しがちなのは、スレッド、`ThreadLocal`、JMX、ドライバ登録、シャットダウンフック、キャッシュライブラリのグローバルレジストリです。

詳細な同一性の話は [JVM とクラスローディング](./jvm-and-classloading) に任せ、ここでは「再デプロイ後に戻らないメモリは、オブジェクトリークとは別ルートを疑う」と覚えてください。

### 内部クラスと隠れた `this`

非 static な内部クラスは、外側のインスタンスへの隠し参照を持ちます。  
コールバックを長く生きる場所へ渡すと、外側の巨大なオブジェクトまで一緒に生きます。  
コールバックは `static` なネストクラスにする、必要な値だけコピーする、外側を弱く持つ、などでグラフを切します。

## 調査の流れ

最初から全コードを読まない方が速いです。

1. 本当に単調増加か、GC 後に戻るかを時系列で確認する
2. ヒープ不足なのか、メタスペースなのか、ネイティブなのかをエラーメッセージと指標で分ける
3. ヒープの問題なら、安全なタイミングでヒープダンプを取る
4. Histogram で「何のインスタンスが多いか」を見る
5. Dominator Tree や Retained Size で「誰が大きな部分木を支配しているか」を見る
6. Path to GC Roots で「なぜ到達可能か」を見る
7. 経路が分かってから、対応するコードの寿命設計を直す

ダンプは **ある瞬間のヒープのスナップショット** です。  
ファイルサイズはヒープ上限に近くなり得ます。  
取得中はアプリケーションが止まったり遅くなったりすることがあります。

```bash
jcmd <pid> GC.heap_dump /tmp/app.hprof
```

プロセス ID は `jcmd` や `jps` で確認します。  
`OutOfMemoryError` の瞬間を自動保存したいときは、起動オプションに次を付けることがあります。

```text
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/var/log/app
```

:::warning[本番のダンプは中身も容量も危険]

ヒープには業務データ、トークン、個人情報が載ることがあります。  
保存先の権限、転送経路、解析後の廃棄を先に決めます。  
ディスク空きが足りないと、ダンプ失敗に加えて別障害になります。  
ピーク中に何度も取ると、停止時間が被害を広げます。

:::

解析には Eclipse MAT、VisualVM、JDK 付属のツール、商用プロファイラなどが使われます。  
製品の操作手順より、次の三つの見方が共通です。

| 見るもの                       | 分かること                                                   |
| ------------------------------ | ------------------------------------------------------------ |
| Histogram                      | どのクラスのインスタンス数が多いか、浅いサイズの合計か       |
| Dominator Tree / Retained Size | そのオブジェクトを消したら、何バイト分がまとめて不要になるか |
| Path to GC Roots               | どの参照の鎖があるため回収されないか                         |

Shallow size はオブジェクト自身の大きさ、Retained size は「これをルートにした部分木」の大きさ、と覚えると Histogram と Dominator の使い分けができます。  
目立つ配列は中身で、目立つ `ConcurrentHashMap$Node` はマップの保持、といった読み替えをします。

特に効くのが Path to GC Roots です。  
灯りからケーブルをたどれ——GC は到達可能なものを回収できないので、「なぜ到達可能なのか」がそのまま修正点になります。

<details>
<summary>OOM のメッセージで先に切り分ける</summary>

- `Java heap space` … オブジェクトグラフがヒープ上限に達した
- `Metaspace` … クラスメタデータ側。ロード数やローダー残留を疑う
- `Unable to create native thread` … スレッド作成時のネイティブメモリや OS 制限
- `Direct buffer memory` … 直接バッファ側の上限

同じ `OutOfMemoryError` でも、次に取る成果物が違います。  
ヒープダンプが有効なのは、主に Java ヒープの話です。

</details>

## コードに戻ったあとの直し方

経路が見えたら、次のどれか（複数）です。

- エントリに上限と期限を付ける。期限切れを実際に消す
- 登録と解除を対にする。`try/finally` で `ThreadLocal#remove`
- キャッシュ対象を弱くする。ただしキー／値の強参照に注意する
- 巨大な結果セットを、一度にリストへ載せない（ストリーム、ページング）
- スレッドプールのキューを有界にし、拒否方針を決める
- 再デプロイ時にグローバル登録を外す

「とりあえず `null` を代入する」は、経路がローカル変数だけなら意味があります。  
経路が `static` なら、代入してもマップがまだ指していれば無意味です。

## よくあるつまずき

- ブレークポイントでオブジェクトを一つずつ追い、全体量を見失う
- Histogram の上位クラスを「犯人」と決め、Root 経路を見ない
- 開発用の短い負荷で「増えて戻った」ことを、本番の長期保持と同じだと思う
- キャッシュライブラリを入れただけで寿命が管理されると信じる
- リーク調査中にヒープ上限だけを上げ、グラフが隠れて再現が遅くなる

## まとめ / 次に学ぶとよいこと

- Java のリークは、到達可能な不要オブジェクトである
- 単調増加か、GC で戻るかを先に見る
- ダンプでは件数より「誰が支配し、どのルートから届くか」
- `static`、リスナー、`ThreadLocal`、無制限キュー、クラスローダーは常連
- 本番ダンプは停止・容量・機密情報の三重で扱う

到達可能な不要オブジェクトを切る話は、いったんここまでです。
