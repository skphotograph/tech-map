# ラムダ・Stream・Optional

ここは、「なんとなく動く」と「自分の言葉で説明できる」の差が出やすい場所です。  
三つを一度に覚える必要はありません。次の順番で進みます。

1. ラムダ式 … その場限りの小さな処理を、値のように渡す書き方
2. Stream … 一覧に対して「残す・変換する・受け取る」をつなげる API
3. Optional … 「無いかもしれない戻り値」を型で表す箱

Stream の中でラムダをよく使うので同一視されがちですが、**別の道具** です。  
Collector や少し長いパイプラインは、あとの [Stream と Collector](./stream-and-collectors) で扱います。  
このページは、入口で思考が止まらないことを目指します。

## このページで分かること

- ラムダ式の読み方（左が引数、右が処理）
- Stream が for ループの何を置き換えるか
- 中間操作と終端操作の違い（なぜ終端まで書かないと動かないか）
- Optional の基本的な使い方と、無理に使わない判断
- Stream にしない方が読みやすい場面

## ステップ1: いまの for ループで何をしているか

一覧から「条件に合うものだけ残し、別の形で受け取る」は、もともとこう書けます。

```java
List<String> openTitles = new ArrayList<>();
for (Task task : tasks) {
    if (task.isOpen()) {
        openTitles.add(task.getTitle());
    }
}
```

やっていることは三つです。

1. 一覧を順に見る
2. 条件で残す（ここでは未完了だけ）
3. 別の値に変換して集める（タイトル）

件数が増え、絞り込みや変換が続くと、一時リストとループ変数が増えて「何をしたいか」が埋もれます。  
ラムダと Stream は、この三つを **目的の言葉に近い形で並べる** ための道具です。

## ステップ2: ラムダ式は「渡す用の短い処理」

いきなり Stream に入らず、まずラムダだけ見ます。

```java
List<String> names = List.of("a", "bb", "ccc");

names.forEach(name -> System.out.println(name));
```

`name -> System.out.println(name)` がラムダ式です。

| 部分 | 意味 |
| ---- | ---- |
| `name` | 受け取る値（引数） |
| `->` | 「左を使って右を行う」という区切り |
| `System.out.println(name)` | 実行する処理 |

「名前を表示する」「長さで並べ替える」など、今回限りの短い処理のために、毎回クラスを用意しなくて済むのがうれしい点です。

値を返すラムダもあります。

```java
name -> name.startsWith("A")   // boolean を返す
name -> name.toUpperCase()     // String を返す
```

`{}` を使わない形では、右側の式の結果がそのまま戻り値になります。  
複数行にするときは `{}` を使い、値を返すなら `return` が必要です。

```java
names.forEach(name -> {
    String upper = name.toUpperCase();
    System.out.println(upper);
});
```

重要なのは、**ラムダが何を返すべきかは、受け取る側の API が決める** ことです。  
あとで見る Stream の `filter` は「残すかどうか」なので `boolean` を返すラムダを渡し、`map` は「変換後の値」を返すラムダを渡します。

```java
names.sort((left, right) -> left.length() - right.length());
```

引数が一つのときは括弧を省略できます。  
メソッド参照 `String::length` のような書き方は、「すでに名前があるメソッドを、そのまま渡す」短縮形です。  
まずは `x -> ...` が読めれば十分です。

:::tip[ここまでのチェック]

ラムダは Stream 専用の文法ではありません。  
「その場限りの小さな振る舞いを、引数として渡す記法」です。

:::

## ステップ3: Stream は「残す・変換する・受け取る」の並べ方

同じ処理を Stream で書くと、次のようになります。

```java
List<String> openTitles = tasks.stream()
        .filter(task -> task.isOpen())
        .map(task -> task.getTitle())
        .toList();
```

ステップ1の for と対応させると、こうです。

| for でやっていたこと | Stream |
| -------------------- | ------ |
| 一覧を順に見る | `tasks.stream()` |
| 条件で残す | `filter(...)` |
| 別の値に変換する | `map(...)` |
| 結果をリストとして受け取る | `toList()` |

読むときは上から、「何を流し、何を残し、何に変え、最後にどう受け取るか」と声に出すと追いやすいです。

```text
tasks を流す
  → 未完了だけ残す
  → タイトルに変える
  → リストとして受け取る
```

件数だけ欲しいなら、受け取り方が変わります。

```java
long openCount = tasks.stream()
        .filter(Task::isOpen)
        .count();
```

`Task::isOpen` は `task -> task.isOpen()` と同じ役割のメソッド参照です。

## ステップ4: 中間操作と終端操作（ここがつまずきやすい）

Stream の操作は、大きく二つに分かれます。

- **中間操作**（`filter`, `map` など）… 「こうする」とつなぐ。まだ結果を確定しないことが多い
- **終端操作**（`toList`, `count`, `forEach` など）… ここで結果が必要になり、処理が進む

```java
tasks.stream()
        .filter(Task::isOpen)
        .map(Task::getTitle);
// 終端が無い。結果のリストは手に入らない
```

「Stream を書いたのに何も起きない」と感じたら、まず終端操作があるかを見ます。  
中間操作はレシピの行、終端操作は「実際に作り始める合図」に近いイメージです。

:::tip[覚えておくこと]

Stream は「流して変換・集計する」道具。  
終端操作まで書かないと、期待した処理が走らないことがある。

:::

一つの Stream に対して終端操作は一度、という感覚も持っておくとよいです。  
使い終わった Stream を、もう一度 `filter` から使い回すものではありません。  
必要なら、元のコレクションから再度 `stream()` します。

## ステップ5: Optional は「無いかもしれない」を戻り値で表す

`Optional<T>` は、値があるかもしれない箱です。  
`null` を返す代わりに、「無い」ことを型で示したいときに使います。

```java
Optional<User> maybe = findUser(userId);

String label = maybe
        .map(User::getName)
        .orElse("unknown");
```

読み方のステップです。

1. `findUser` は、ユーザーが居ないかもしれない
2. 居れば名前へ変換する（`map`）
3. 居なければ `"unknown"` を使う（`orElse`）

`get()` をいきなり呼ぶと、空のときに例外になります。  
「無かったときどうするか」を、`orElse` / `orElseThrow` / `ifPresent` などで先に決める使い方が安全です。

<details>
<summary>フィールドや引数に Optional を置かない方がよい理由</summary>

Optional は主に **戻り値** 向きの型、という考え方が一般的です。  
フィールドや引数まで Optional だらけにすると、かえって冗長になります。  
「無さ」をどう表すかは、API ごとに一貫させます。  
また、`Optional` 変数自体を `null` にはしません。箱が無い、という意味が二重になってしまいます。

</details>

Stream の `findFirst` や `max` が `Optional` を返すのも、同じ発想です。  
「0 件かもしれない結果」を、null ではなく型で受け取ります。  
詳しいつなぎ方は [Stream と Collector](./stream-and-collectors) へ続きます。

## ステップ6: 無理に Stream にしない

次のようなときは、普通の for や早期 return の方が読みやすいことが多いです。

- ループ内で複数の可変状態を更新する（単純な filter / map に収まらない）
- 例外やログを細かく分岐したい
- 処理が短く、Stream にすると逆に層が増える

```java
for (Task task : tasks) {
    if (task.isOpen()) {
        notifier.notifyUser(task.getOwnerId());
    }
}
```

「モダンだから Stream」ではなく、**読み手が追いやすいか** で選びます。  
副作用（通知、保存、ログ）が本体のときは、パイプラインより文の並びの方が意図が伝わることがあります。

## よくあるつまずき

- ラムダと Stream を同じものだと思い、どちらの話か分からなくなる
- 中間操作だけ書いて終端を忘れ、何も起きないと驚く
- Optional の `get()` を連鎖して、NPE より分かりにくい例外になる
- 副作用の多い処理を `map` に押し込み、パイプラインの意図が濁る

## まとめ / 次に学ぶとよいこと

思考の順番だけでも、次に進めます。

1. for でやっている「残す・変換する・集める」を言葉にする
2. ラムダは、その小さな処理を渡す書き方
3. Stream は、それを上から並べる API。終端で結果が確定する
4. Optional は、無いかもしれない戻り値の箱
5. 読みやすさで for に戻してよい

次は [確認クイズ](./practice) で、ここまでの理解を短く点検します。  
Stream の集計や `groupingBy` は、あとから [Stream と Collector](./stream-and-collectors) で積み上げます。
