# レイヤーと DI

機能追加のたびに Controller へ処理を書き足すと、HTTP、業務ルール、SQL が一つのクラスに集まりがちです。  
変更理由の異なる処理をレイヤーに分け、DI でつなぐと、役割と依存関係を追いやすくなります。

## このページで分かること

- Controller、Service、Repository（DAO）の代表的な責務
- DI（Dependency Injection）が解決する課題
- Jakarta の `@Inject` と Spring の `@Autowired` に共通する考え方

## 代表的な三つのレイヤー

Web アプリケーションでは、次のような分け方がよく見られます。

- Controller: HTTP の入力を受け取り、応答へ変換する
- Service: ユースケースや業務ルールを実行する
- Repository / DAO: データの保存や取得を隠蔽する

設計の入口で見た [レイヤードアーキテクチャと MVC](../design/layered-and-mvc) の四層は、業務の地図です。  
ここでいう三層は Web 実装での通称で、だいたい次のように対応します。

- Presentation ≈ Controller
- Application / Domain ≈ Service
- Infrastructure ≈ Repository

Repository はドメインの言葉でデータの集合を扱うことが多く、DAO はテーブルや SQL に近い操作を表すことが多い名前です。  
ただし、用語の使い分けはプロジェクトによって異なるため、名前より実際の責務を確認します。

```java
public final class OrderService {
    private final OrderRepository orderRepository;

    public OrderService(OrderRepository orderRepository) {
        this.orderRepository = orderRepository;
    }

    public Order find(long orderId) {
        return orderRepository.findById(orderId)
            .orElseThrow(() -> new OrderNotFoundException(orderId));
    }
}
```

`OrderService` は、保存方法を知るのではなく、`OrderRepository` が提供する操作へ依存しています。  
この境界があると、データベース実装の詳細を Service から切り離せます。

## DI は依存する部品を外から渡す仕組み

DI は Dependency Injection、つまり依存性の注入です。  
クラス自身が必要な実装を生成する代わりに、外部の組み立て役から受け取ります。  
コンストラクタで依存を渡す考え方は [リファクタリングの道具箱](../design/refactoring-toolkit) でも触れました。ここではコンテナのアノテーションまで含めて見ます。

:::tip[アノテーションは宣言]

`@Inject` や `@Autowired` は「ここに注入して」という宣言です。  
実際に読む・組み立てる主体はコンテナ側です。仕組みの入口は [アノテーションとリフレクション](../basics/annotations-reflection) を参照してください。

:::

```java
OrderRepository repository = new JdbcOrderRepository(dataSource);
OrderService service = new OrderService(repository);
```

この例では、コンストラクターを通して依存する部品を渡しています。  
DI コンテナを使わなくても、これ自体が DI です。

DI コンテナは、登録された部品の生成、依存関係の解決、ライフサイクル管理を支援します。  
Jakarta Contexts and Dependency Injection（CDI）では `@Inject`、Spring では `@Autowired` が注入を示す例です。

```java
@Inject
public OrderService(OrderRepository orderRepository) {
    this.orderRepository = orderRepository;
}
```

```java
@Autowired
public OrderService(OrderRepository orderRepository) {
    this.orderRepository = orderRepository;
}
```

どちらも「必要な `OrderRepository` を実行基盤に渡してもらう」という考え方は共通です。  
Spring では、コンストラクターが一つなら `@Autowired` を省略できる場合があります。

:::tip[コンストラクターで依存を明示する]

必須の依存をコンストラクター引数にすると、生成時点で不足に気付きやすく、単体テストでも差し替えやすくなります。

:::

## レイヤーを分ける判断

レイヤーは、クラス数を増やすこと自体が目的ではありません。  
HTTP の都合、業務ルール、保存方式という異なる変更理由を分離するために使います。

小さな参照処理で Service が単なる中継になる場合もあります。  
将来を想像して層を増やしすぎず、プロジェクトの規約と変更の見込みに合わせます。

## よくあるつまずき

- Controller へ SQL やトランザクション処理まで書く
- Service が HTTP のステータスコードへ直接依存する
- Repository が画面表示用の形式まで組み立てる
- DI コンテナが管理する部品を `new` して、注入や共通処理を迂回する
- レイヤーごとに必ずクラスを作り、意味のない転送だけを増やす

## まとめ

- Controller、Service、Repository は変更理由の異なる責務を分ける目安である
- DI は必要な部品を外から渡し、実装の結合を弱める
- `@Inject` と `@Autowired` は異なる仕組みの API だが、依存を注入する目的は共通する
- レイヤー数ではなく、責務と依存の向きが明確かを確認する
