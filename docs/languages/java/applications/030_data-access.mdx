# データアクセス

一覧取得は速いのに詳細画面で問い合わせが大量に走る、更新途中で例外が起きて一部だけ保存される——こうした問題は、データアクセスの抽象化だけでは防げません。  
利用する方式の特徴と、実際に発行される問い合わせ、トランザクション境界を一緒に理解する必要があります。

## このページで分かること

- DAO / Repository と JDBC の関係
- JPA、MyBatis、Spring Data の特徴とトレードオフ
- トランザクション境界を Service 層に置く理由

## DAO / Repository で保存方法を隠す

Service からデータベースの詳細を切り離すため、DAO や Repository に取得・保存処理をまとめます。

```java
public interface OrderRepository {
    Optional<Order> findById(long orderId);

    void save(Order order);
}
```

このインターフェースだけでは、JPA、MyBatis、JDBC のどれを使うかは決まりません。  
実装側でプロジェクトに合う方式を選びます。

## 下層では JDBC につながる

JDBC は、Java からリレーショナルデータベースへ接続し、SQL を実行する標準 API です。  
JPA の実装や MyBatis なども、通常は下層で JDBC の接続を利用します。

上位の仕組みを使っても、接続プール、実行 SQL、バインド値、トランザクション、ロックの理解は障害調査に必要です。  
棚札だけ見て倉庫の中を見ない——では遅い・壊れたときに原因へ届きません。  
JDBC の基本は [JDBC の基礎](../basics/jdbc-basics) で確認できます。

## JPA: オブジェクトと関係モデルを対応付ける

JPA（Jakarta Persistence）は、Entity とテーブルの対応付けや永続化コンテキストを定めた仕様です。  
実際の動作は JPA 実装が提供します。

Entity の関連や状態変化を中心に扱えるため、業務モデルとオブジェクト操作を結び付けやすい特徴があります。  
一方で、遅延読み込み、キャッシュ、変更検知を理解していないと、予想外の問い合わせや更新が生じることがあります。

## MyBatis: SQL を明示して対応付ける

MyBatis は、SQL と Java オブジェクトの対応付けを支援する SQL マッパーです。  
複雑な検索やデータベース固有の機能を使う場面で、発行する SQL を明示的に制御しやすい特徴があります。

一方で、SQL、結果のマッピング、スキーマ変更への追従をアプリケーション側で管理します。  
類似した CRUD の SQL が増える場合は、共通化と可読性のバランスを考えます。

## Spring Data: Repository 実装を支援する

Spring Data は、Repository 抽象化や実装生成を支援する Spring のプロジェクト群です。  
たとえば Spring Data JPA は JPA の上に構築され、Repository インターフェースから定型的なデータ操作を組み立てます。

定型コードを減らせる一方、メソッド名から生成される問い合わせ、JPA の挙動、Spring のトランザクション管理を理解する必要があります。  
Spring Data は JPA と対立する分類ではなく、JPA などのデータアクセス技術を利用しやすくする層として捉えます。

## 選択時に見る観点

| 観点         | JPA                           | MyBatis                   | Spring Data JPA              |
| ------------ | ----------------------------- | ------------------------- | ---------------------------- |
| 主な抽象化   | Entity と関連                 | SQL と結果マッピング      | JPA Repository               |
| SQL の制御   | 実装が生成する部分が多い      | 明示しやすい              | JPA に準じる                 |
| 定型 CRUD    | 少ないコードで表しやすい      | SQL とマッピングを書く    | さらに省略しやすい           |
| 学ぶべき挙動 | Entity 状態、関連、キャッシュ | SQL、マッピング、動的 SQL | JPA に加えて Repository 規約 |

どれか一つが常に優れているわけではありません。  
データモデル、問い合わせの複雑さ、SQL 制御の必要性、チームの経験、既存資産から判断します。  
同じアプリケーション内で用途別に併用する構成もありますが、トランザクションや保守方法が複雑にならないか確認します。

:::tip[抽象化の下を観察する]

方式を問わず、開発時に実行 SQL と件数、トランザクション範囲を確認できるようにしておくと、性能問題や不整合を早く見つけられます。

:::

## トランザクション境界

一つのユースケースで複数の更新を行う場合、まとめて成功または失敗させます。  
そのため、トランザクション境界は Repository の個別メソッドではなく、ユースケースを表す Service メソッドに置くことがよくあります。  
`commit` / `rollback` の手元イメージは [JDBC の基礎](../basics/jdbc-basics) を参照してください。  
フレームワークは、その境界を宣言的に張ることが多いです。

```java
public void placeOrder(PlaceOrderCommand command) {
    orderRepository.save(createOrder(command));
    inventoryRepository.reserve(command.items());
}
```

この二つを同じトランザクションに含めるかは、データの一貫性要件によって決まります。  
外部 API 呼び出しを含む場合は、データベーストランザクションだけでは原子的に扱えないため、別の設計も必要です。

## よくあるつまずき

- ORM やマッパーを使えば SQL を調べなくてよいと考える
- JPA の遅延読み込みによる N+1 問題を見逃す
- 一覧処理で一件ずつ更新し、不要に多くの SQL を発行する
- トランザクションを広げすぎ、接続やロックを長時間保持する
- 例外を握りつぶし、必要な rollback が行われない

## まとめ

- DAO / Repository は Service から保存方式の詳細を切り離す
- JPA と MyBatis は、モデル中心か SQL 中心かという異なる強みを持つ
- Spring Data は JPA などの上で Repository 実装を支援する
- 選択した方式にかかわらず、JDBC、発行 SQL、トランザクションを理解する
