# 可観測性と JSON

利用者から「エラーになった」と連絡を受けても、応答形式がばらばらで、ログに対象リクエストを探す手掛かりがなければ調査に時間がかかります。  
クライアント向けの構造化エラーと、運用者向けのログを役割分担させることが重要です。  

## このページで分かること

- 構造化したエラー応答に含める情報
- ログレベルと記録内容の考え方
- JSON マッピングと Jackson の位置付け

## エラーを構造化して返す

エラー本文を一定の JSON 構造にすると、クライアントは文字列解析ではなく項目として処理できます。  

```json
{
  "code": "ORDER_NOT_FOUND",
  "message": "指定された注文は見つかりません",
  "requestId": "01J8EXAMPLE"
}
```

`code` はプログラムが分岐に使える安定した識別子、`message` は利用者向けの説明です。  
`requestId` は応答とサーバログを対応付ける手掛かりになります。  

入力エラーでは、問題のある項目を配列で返す設計もあります。  
どの形式を使う場合も、API 全体で項目名と HTTP ステータスの対応をそろえます。  

:::warning[内部情報を応答へ出さない]

スタックトレース、SQL、ファイルパス、秘密情報をエラー応答へ含めません。  
調査用の詳細はアクセス制御されたログへ記録します。  

:::

## ログレベルを使い分ける

ログレベルは、情報の重要度と運用時の扱いを表します。  
一般的な目安は次のとおりです。  

- `ERROR`: 処理を完了できず、調査や対応が必要な失敗
- `WARN`: 処理は継続できるが、放置すると問題になり得る状態
- `INFO`: 起動、停止、主要な処理結果など通常運用で必要な情報
- `DEBUG`: 開発や詳細調査で利用する内部状態
- `TRACE`: 呼び出し単位など、さらに細かな追跡情報

同じ出来事を複数層で `ERROR` として記録すると、一件の障害が何件にも見えます。  
例外を最終的に処理する境界で、必要な文脈とともに一度記録する方針を決めます。  

ログには時刻、レベル、リクエスト ID、処理名などを構造化して含めると検索しやすくなります。  
注文 ID のような調査キーは役立ちますが、個人情報や資格情報を記録してよいとは限りません。  

:::tip[メッセージより検索項目をそろえる]

文章だけでなく、`requestId`、`orderId`、`errorCode` などを一貫した項目名で記録すると、ログを集約した後も絞り込みやすくなります。  

:::

## Java オブジェクトと JSON の変換

REST API では、Request DTO の JSON を Java オブジェクトへ読み込み、Response DTO を JSON へ書き出します。  
この処理をシリアライズとデシリアライズと呼びます。  

Jackson は Java で広く使われる JSON 処理ライブラリの一つです。  
Spring の Web 機能などで標準的に組み込まれることがありますが、Jakarta EE のランタイムや別のスタックでは JSON-B など他の仕組みも選択できます。  

```java
public record OrderResponse(
    long orderId,
    String status
) {
}
```

このような DTO は、JSON マッパーによって次の形式へ変換できます。  

```json
{
  "orderId": 42,
  "status": "ACCEPTED"
}
```

日時、列挙型、未知の項目、`null` の扱いは、ライブラリや設定によって変わります。  
既定動作に任せたままにせず、API の契約として形式を決め、テストで確認します。  

## ログに残すもの、残さないもの

調査に必要だからといって、リクエストやレスポンスの本文を無条件に記録するのは危険です。  
パスワード、トークン、個人情報、決済情報などが含まれる可能性があります。  

本文の記録が必要な場合は、対象環境、保存期間、アクセス権、マスキング方法を決めます。  
通常はリクエスト ID、処理結果、所要時間、公開してよい識別子を優先します。  

## よくあるつまずき

- エラーごとに異なる JSON 形式を返す
- `500` 応答へ例外メッセージやスタックトレースを含める
- 想定内の入力エラーをすべて `ERROR` で記録する
- 同じ例外を各レイヤーで繰り返し記録する
- DTO の日時形式や未知項目の扱いを既定値のまま公開契約にする
- リクエスト本文をそのままログへ記録する

## まとめ

- エラー応答はコード、メッセージ、追跡用 ID などを一定の構造で返す
- ログレベルは運用上の重要度に合わせ、同じ失敗を重複して記録しない
- Jackson は一般的な選択肢の一つであり、利用環境には他の JSON マッピング方式もある
- API の JSON 形式は明示的に決め、変換結果をテストする
- ログへ秘密情報や個人情報を残さない
