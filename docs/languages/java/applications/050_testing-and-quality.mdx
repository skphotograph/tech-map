# テストと品質

一つのテストを実行するたびにサーバとデータベースの起動を待っていると、確認の回数が減り、失敗原因も追いにくくなります。  
レイヤーごとの責務を小さく確認するテストと、実際の接続を確認するテストを組み合わせることが大切です。  

## このページで分かること

- JUnit を使った単体テストの基本的な形
- Mockito などのテストダブルを使う目的
- コンテナ全体を起動しないテストと統合テストの使い分け
- レイヤー規約を品質につなげる考え方

## JUnit で振る舞いを確認する

JUnit は Java で広く使われるテストフレームワークです。  
入力、実行、期待結果を分けて書くと、何を確認しているか読み取りやすくなります。  

```java
class OrderServiceTest {
    @Test
    void returnsOrderWhenItExists() {
        Order order = new Order(42L);
        OrderRepository repository = new InMemoryOrderRepository(order);
        OrderService service = new OrderService(repository);

        Order actual = service.find(42L);

        assertEquals(42L, actual.id());
    }
}
```

このテストは通常の Java オブジェクトを生成しており、HTTP サーバや DI コンテナを起動していません。  
Service の業務判断を短時間で確認できます。  

## テストダブルで境界を置き換える

データベースや外部 API の代わりになる部品をテストダブルと呼びます。  
手作りのインメモリ実装、固定値を返す Stub、呼び出しを検証する Mock などがあります。  

Mockito は、Mock を作るために広く使われるライブラリです。  

```java
OrderRepository repository = mock(OrderRepository.class);
when(repository.findById(42L))
    .thenReturn(Optional.of(new Order(42L)));

OrderService service = new OrderService(repository);

assertEquals(42L, service.find(42L).id());
verify(repository).findById(42L);
```

Mock は依存先の異常系や呼び出しを表しやすい一方、内部の呼び出し手順へテストが強く結合することがあります。  
戻り値だけで振る舞いを確認できるなら、手作りの実装や Stub のほうが変更に強い場合もあります。  

:::tip[速いテストだけで完結させない]

単体テストは業務判断を素早く確認し、統合テストは設定、SQL、JSON 変換など部品間の接続を確認します。  

:::

## コンテナを起動する範囲を選ぶ

テスト対象に応じて、起動範囲を変えます。  

- 単体テスト: 通常のオブジェクトだけで Service や変換処理を確認する
- レイヤーテスト: HTTP 境界やデータアクセスなど、必要な部分だけを起動する
- 統合テスト: DI、トランザクション、実データベースとの接続などを確認する
- エンドツーエンドテスト: 外部からアプリケーション全体の主要な流れを確認する

Jakarta EE 系のランタイムにも Spring 系のテスト機能にも、必要な範囲を起動する仕組みがあります。  
名称や機能は異なるため、利用するランタイムの公式ドキュメントで確認します。  

実データベースに依存する SQL や制約は、インメモリの代替データベースだけでは差異を見逃すことがあります。  
本番と同系統のデータベースを隔離されたテスト環境で使う方法も検討します。  

## レイヤー規約を守る

レイヤー構成は、図に書くだけでは時間とともに崩れます。  
コードレビューや静的解析で、依存方向と命名規則を確認します。  

代表的な規約には、次のものがあります。  

- Controller は Repository を直接呼ばない
- Service は HTTP 型へ依存しない
- ドメインの型はフレームワーク固有 API への依存を必要最小限にする
- 外部アクセスはインターフェースの境界を通す

規約は多ければよいわけではありません。  
違反したときの問題が説明でき、チームで継続して確認できるものに絞ります。  

## よくあるつまずき

- すべてのテストでアプリケーション全体を起動する
- Mock の呼び出し回数だけを検証し、利用者から見た結果を確認しない
- データベース製品ごとの差がある SQL を代替実装だけでテストする
- テスト間でデータを共有し、実行順によって結果が変わる
- レイヤー規約を文書化するだけで、自動検査やレビューの観点に含めない

## まとめ

- JUnit で小さな振る舞いを素早く確認する
- Mockito は有効な選択肢だが、実装手順への過度な結合に注意する
- 単体、レイヤー、統合、エンドツーエンドのテストを目的に応じて組み合わせる
- レイヤー規約は、レビューや静的解析で継続的に守る
