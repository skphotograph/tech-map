# アプリケーション部品

フレームワークのサンプルは動いたのに、実際のプロジェクトを開くと `Controller`、`Service`、`Repository`、DTO などが一度に現れ、どこから読めばよいか迷うことがあります。  
名前やアノテーションは製品ごとに違っても、業務アプリケーションを支える考え方には多くの共通点があります。

:::info[この章の前提]

[設計の入口](../design/)（特に [レイヤードアーキテクチャと MVC](../design/layered-and-mvc)）と [Maven](../maven/) を読んでいると追いやすいです。  
アノテーションが「宣言だけ」であることは [アノテーションとリフレクション](../basics/annotations-reflection) を参照してください。

:::

## この章で分かること

- エンタープライズ Java アプリケーションを構成する代表的な部品
- DI、REST、データアクセス、横断的関心事が解決する課題
- Jakarta EE と Spring、JPA と MyBatis などの選択肢を比較する観点
- テスト、ログ、JSON を含めて運用可能なアプリケーションにする考え方

## 製品名より先に役割を捉える

Java の業務アプリケーションでは、Jakarta EE の API をアプリケーションサーバで使う構成も、Spring Framework と Spring Boot を中心に組み立てる構成も一般的です。  
両者には実行環境や設定方法の違いがありますが、リクエストを受け、業務処理を実行し、データを保存して応答するという基本の流れは共通します。

この章では、特定のスタックを正解として選ぶのではなく、コードを読んだときに「この部品は何を担当しているか」を説明できることを目指します。

:::tip[この章のゴール]

製品固有のアノテーションを暗記する前に、層の責務、依存関係、データ境界、トランザクション境界を見つけられるようになりましょう。

:::

## まとめ

- 業務アプリケーションの部品には、スタックをまたいで共通する役割がある
- Jakarta EE と Spring はどちらも一般的な選択肢であり、実行環境やチームの条件で選ぶ
- 製品固有の書き方より先に、責務と境界を理解するとコードを追いやすくなる
