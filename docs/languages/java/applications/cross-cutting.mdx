# 横断的な機能

各 Controller に入力検証、認証確認、処理時間のログを同じように書くと、少しずつ挙動がずれ、修正漏れも起きます。  
複数の機能を横断する処理は、目的に合った共通の仕組みへ置くと一貫して適用できます。  

## このページで分かること

- 入力検証を境界で行う考え方
- Filter、Interceptor、Middleware に共通する役割
- 環境ごとの設定と秘密情報の扱い
- 認証と認可をアプリケーションへ組み込む入口

## 入力を境界で検証する

必須項目、文字数、数値範囲、形式などは、Request DTO を受け取る境界で検証します。  
Jakarta Validation の制約アノテーションは、Jakarta EE でも Spring でも利用される代表的な方法です。  

```java
public record CreateOrderRequest(
    @Positive long userId,
    @NotEmpty List<OrderItemRequest> items
) {
}
```

形式上の検証と、業務ルールの検証は分けて考えます。  
たとえば「数量が正の値」は入力制約として確認できますが、「この利用者が注文可能か」は Service が現在の状態を使って判断します。  

:::tip[検証する場所を決める]

形式は外部との境界、業務ルールはユースケース内というように責務を決めると、同じ検証の重複を減らせます。  

:::

## Filter、Interceptor、Middleware

名称と適用範囲はスタックによって異なりますが、リクエストの前後へ共通処理を差し込む考え方は共通します。  

代表的な用途には、次のものがあります。  

- リクエスト ID の付与
- アクセスログや処理時間の記録
- 認証情報の読み取り
- 共通ヘッダーの設定
- 例外から共通エラー応答への変換

Filter は HTTP や Servlet に近い位置、Interceptor は Controller や Service の呼び出しに近い位置で使われることがあります。  
「どのリクエストに、どの順番で、例外時にも適用されるか」を利用する仕組みの仕様で確認します。  

共通化できるからといって、業務ルールまで横断処理へ隠すと呼び出し関係が追いにくくなります。  
注文可否の判定などは Service へ明示的に置きます。  

## 環境ごとに設定を切り替える

開発、テスト、本番では、データベース接続先、ログレベル、外部 API の URL などが異なります。  
コードを環境ごとに変更するのではなく、設定ファイル、環境変数、実行基盤の設定機能などから注入します。  

設定項目には既定値を設けられるものと、起動時に必須とすべきものがあります。  
本番で必須の接続先がなければ、安全でない値へ暗黙にフォールバックせず、起動を失敗させる判断も必要です。  

:::warning[秘密情報をリポジトリへ保存しない]

パスワード、API キー、トークンは通常の設定ファイルへ直接書かず、実行環境のシークレット管理機能などから渡します。  

:::

## 認証と認可

認証（Authentication）は「誰であるか」を確認することです。  
認可（Authorization）は「その利用者が操作してよいか」を判断することです。  

一般的には、HTTP 境界で資格情報を検証し、認証済みの主体や権限を後続処理へ渡します。  
エンドポイントやメソッドへのアクセス制御はフレームワークの機能を利用できますが、注文の所有者だけが変更できるといったデータ依存の判断は業務処理でも必要です。  

認証方式を独自に組み立てると、署名検証、セッション管理、失効、時刻など多くの安全上の論点が生じます。  
採用する標準方式とセキュリティ基盤の仕様に従い、秘密情報や個人情報をログへ残さないようにします。  

## よくあるつまずき

- 形式検証だけで、現在の状態に依存する業務ルールも満たしたと思う
- Filter や Interceptor の適用順序を確認しない
- 開発用の既定値が本番でも使われる
- 設定ファイルにパスワードやトークンをコミットする
- 認証済みであることだけを確認し、対象データへの操作権限を確認しない

## まとめ

- 形式上の入力制約は境界で、業務ルールはユースケース内で検証する
- Filter、Interceptor、Middleware は複数処理へ共通機能を適用する考え方である
- 環境差は外部設定として注入し、秘密情報をソース管理しない
- 認証と認可を区別し、データに依存する権限も確認する
