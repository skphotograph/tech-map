# ビルド設定と settings.xml

Java の版を変えたのにコンパイラーの動きが変わらない、テストクラスがあるのに実行されない。  
このようなときは、依存ライブラリではなく、ビルド処理を実行するプラグインの設定を確認します。  
さらに、認証情報やミラー URL のような環境固有情報は、プロジェクトで共有する POM から分離する必要があります。

## このページで分かること

- Maven プラグインとゴールの役割
- Compiler Plugin と Surefire Plugin の基本設定
- `pluginManagement` と `plugins` の違い
- プロファイルを使う場面と避けたい使い方
- `settings.xml` の mirrors、servers に置く情報

## プラグインが実際の処理を行う

Maven のライフサイクルはビルドの段階を定義し、各段階の具体的な処理はプラグインのゴールが実行します。  
たとえば、Java ソースのコンパイルは Maven Compiler Plugin、単体テストの実行は Maven Surefire Plugin が担当します。

プラグインは `build` の `plugins` に宣言できます。  
バージョンを明示すると、Maven や親 POM の違いによる変化を抑え、ビルドを再現しやすくなります。

## Compiler Plugin で Java の版を指定する

次は、Java 17 の API とバイトコードを対象にコンパイルする設定です。

```xml
<build>
  <plugins>
    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-compiler-plugin</artifactId>
      <version>3.13.0</version>
      <configuration>
        <release>17</release>
      </configuration>
    </plugin>
  </plugins>
</build>
```

`release` は、生成する class ファイルの対象版だけでなく、その Java 版で利用可能な標準 API も制約します。  
古い実行環境向けにビルドする場合、単に `source` と `target` を合わせるより、意図しない新しい API の利用を検出しやすくなります。

コンパイルは次のコマンドで確認できます。

```bash
mvn compile
```

成功時の末尾には次のように表示されます。

```text
[INFO] ------------------------------------------------------------------------
[INFO] BUILD SUCCESS
[INFO] ------------------------------------------------------------------------
```

ログ中の `maven-compiler-plugin` の行から、実行されたプラグインのバージョンとゴールを確認できます。

## Surefire Plugin で単体テストを実行する

Surefire Plugin は、通常 `test` フェーズで単体テストを実行します。

```xml
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-surefire-plugin</artifactId>
  <version>3.5.2</version>
</plugin>
```

`mvn test` が成功すると、テスト件数と結果が表示されます。

```text
[INFO] Tests run: 4, Failures: 0, Errors: 0, Skipped: 0
[INFO] ------------------------------------------------------------------------
[INFO] BUILD SUCCESS
```

`Tests run` が想定した件数か、`Failures` と `Errors` が 0 かを確認します。  
`BUILD SUCCESS` でもテスト件数が 0 なら、命名規則、テストエンジン、プラグイン設定を調べます。

:::tip[成功表示だけでなくテスト件数を見る]

テストビルドでは `BUILD SUCCESS` に加えて、意図したテストが検出・実行されたかを件数で確認します。

:::

<details>
<summary>単体テストと結合テストを分ける場合</summary>

Surefire Plugin は主に `test` フェーズの単体テストに使います。  
結合テストを `integration-test` と `verify` の流れで実行する場合は、Maven Failsafe Plugin が利用できます。  
テストの分類、命名規則、実行するフェーズをプロジェクトで統一し、CI がどこまで実行するかを明確にします。
</details>

## pluginManagement と plugins

親 POM で複数モジュールのプラグインバージョンや既定設定をそろえるには、`pluginManagement` を使えます。  
ただし、通常は `pluginManagement` に置いただけでは、そのプラグインの独自ゴールが実行されるとは限りません。  
利用するモジュールの `plugins` で宣言したときに、管理したバージョンと設定が適用されます。

```xml
<build>
  <pluginManagement>
    <plugins>
      <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <artifactId>maven-surefire-plugin</artifactId>
        <version>3.5.2</version>
      </plugin>
    </plugins>
  </pluginManagement>
</build>
```

`dependencyManagement` と `dependencies` の関係に似ていますが、対象はビルドプラグインです。  
どのモジュールでも必要な設定と、一部のモジュールだけが必要な実行を分けると、親 POM が過剰な処理を押し付けることを防げます。

## プロファイルで条件付き設定を切り替える

プロファイルは、条件に応じて POM の一部を追加・変更する仕組みです。  
たとえば、特定の JDK でだけ必要な検証や、リリース時だけ有効にする署名処理などに利用できます。

```xml
<profiles>
  <profile>
    <id>release-checks</id>
    <build>
      <plugins>
        <!-- リリース時だけ使う検証プラグインを宣言する -->
      </plugins>
    </build>
  </profile>
</profiles>
```

プロファイルを明示的に有効化する場合は、`-P` を使います。

```bash
mvn verify -Prelease-checks
```

成功時は通常のビルドと同じく末尾に `BUILD SUCCESS` が表示されます。  
ログのプラグイン実行行を見て、プロファイルで追加した検証が実際に動いたことも確認します。

プロファイルで本番・開発のアプリケーション設定を大量に切り替えると、同じ座標の成果物でも内容が異なる状態を作りやすくなります。  
接続先や秘密情報は実行時設定として外部から与え、可能な限り同じ成果物を各環境へ配布します。

## settings.xml は実行環境の設定を置く

`settings.xml` は Maven を実行するユーザーや環境に属する設定です。  
ユーザー単位では通常 `~/.m2/settings.xml`、Maven 全体では Maven の `conf/settings.xml` に置かれます。

POM と `settings.xml` の役割は次のように分けます。

- POM: 依存関係、プラグイン、ビルド方法など、プロジェクトで共有する情報
- `settings.xml`: 認証情報、ミラー、ローカルリポジトリなど、実行環境に属する情報

### mirrors で取得先を集約する

組織が管理するプライベートな Maven レジストリを、外部リポジトリのプロキシやミラーとして使う場合があります。  
`mirrors` では、どのリポジトリへの要求をどの URL へ振り向けるかを設定します。

```xml
<settings>
  <mirrors>
    <mirror>
      <id>organization-mirror</id>
      <name>Organization Maven Mirror</name>
      <url>https://packages.example.com/maven/public</url>
      <mirrorOf>*</mirrorOf>
    </mirror>
  </mirrors>
</settings>
```

`mirrorOf` が `*` の場合、すべてのリポジトリ要求が指定したミラーへ向かいます。  
許可されるリポジトリや障害時の運用に影響するため、組織のレジストリ管理方針に合わせます。

### servers で認証先を識別する

認証が必要なレジストリへの資格情報は、`servers` に設定します。  
`server` の `id` は、POM の配布先や `mirror` などで使う ID と一致させます。

```xml
<settings>
  <servers>
    <server>
      <id>organization-releases</id>
      <username>${env.MAVEN_REPOSITORY_USER}</username>
      <password>${env.MAVEN_REPOSITORY_TOKEN}</password>
    </server>
  </servers>
</settings>
```

この例は、資格情報を環境変数から受け取ります。  
実際のユーザー名やトークンを POM、`settings.xml` のひな型、Git リポジトリへ直接書きません。  
CI ではシークレット管理機能から環境変数や一時的な設定ファイルとして渡します。

:::warning[資格情報をコミットしない]

POM や Git 管理下の `settings.xml` に、パスワードやトークンを平文で保存しません。  
漏えいした可能性がある場合は、履歴から消すだけでなく資格情報を失効・再発行します。

:::

## 実効設定を確認する

親 POM やプロファイルを統合した実効 POM は、次のコマンドで確認できます。

```bash
mvn help:effective-pom
```

環境側の設定を統合した実効 settings は、`mvn help:effective-settings` で確認できます。  
出力には利用環境の情報が含まれる可能性があるため、共有前に URL、ユーザー名、資格情報に関わる内容を確認します。

## よくあるつまずき

- 依存ライブラリとビルドプラグインを同じものとして扱う
- プラグインのバージョンを暗黙の既定値に任せ、環境差が生じる
- `pluginManagement` に書けば、すべてのゴールが自動実行されると考える
- プロファイルごとに異なる成果物を作り、どれを配布したか分からなくなる
- POM にレジストリのパスワードやトークンを記録する

## まとめ

- ライフサイクルの具体的な処理はプラグインのゴールが担当する
- Compiler Plugin はコンパイル対象、Surefire Plugin は単体テスト実行を制御する
- `pluginManagement` はプラグインの版と既定設定を統一する
- プロジェクト共通の設定は POM、認証やミラーなど環境固有の設定は `settings.xml` に分ける
- 秘密情報は Git に保存せず、環境変数やシークレット管理機能から渡す
