# Maven の全体像と POM

ライブラリの JAR ファイルを手作業で集めると、更新漏れやバージョン違いが起きやすくなります。  
さらに、コンパイル方法や成果物の名前まで口頭で共有していると、環境を作り直すたびに同じ確認が必要です。  
Maven は、プロジェクトの情報とビルド方法を POM に記録し、依存関係の取得から成果物の作成までを再現できるようにします。  

## このページで分かること

- Maven が依存管理とビルドで解決する課題
- `groupId`、`artifactId`、`version` からなる座標
- `packaging` と `dependencies` の役割
- 最小限の `pom.xml` の読み方

## Maven がそろえるもの

Maven は、Project Object Model（POM）を中心に動く Java 向けのビルドツールです。  
通常はプロジェクト直下の `pom.xml` に、プロジェクトの識別情報、依存関係、ビルド設定などを記述します。  

Maven を使うと、主に次の内容を共有できます。  

- どのライブラリの、どのバージョンが必要か
- ソースコードとテストコードをどこから読むか
- どの Java バージョンでコンパイルするか
- テスト、パッケージ化、配布をどの順序で行うか
- 作成した成果物を何という名前で識別するか

Maven がインストールされているかは、次のコマンドで確認します。  

```bash
mvn --version
```

代表的な出力は次のとおりです。  

```text
Apache Maven 3.9.9
Maven home: /opt/apache-maven
Java version: 17.0.12, vendor: Eclipse Adoptium
Default locale: ja_JP, platform encoding: UTF-8
OS name: "linux", version: "6.8.0", arch: "amd64"
```

先頭で Maven のバージョンを、`Java version` で Maven 自身が使っている Java のバージョンを確認します。  
ビルドが端末によって異なるときは、まずこの 2 つを比べると原因を絞りやすくなります。  

## 座標で成果物を識別する

Maven は、成果物や依存関係を「座標」で一意に識別します。  
基本となる要素は `groupId`、`artifactId`、`version` の 3 つです。  

- `groupId`: 作成主体やプロジェクト群を表す名前で、通常は逆ドメイン名に似た形式を使う
- `artifactId`: そのグループ内で成果物を識別する名前
- `version`: 成果物の版

たとえば `com.example:order-api:1.0.0` は、`com.example` グループの `order-api` という成果物の `1.0.0` 版を表します。  
依存関係を指定するときも、自分のプロジェクトを公開するときも同じ考え方を使います。  

:::info[座標とファイル名は別のもの]

座標は成果物をリポジトリ上で識別する情報です。  
JAR のファイル名だけを見て管理するより、作成主体とバージョンを含めて区別できます。  

:::

## packaging で成果物の種類を決める

`packaging` は、プロジェクトが作る成果物の種類を表します。  
代表的な値は次のとおりです。  

- `jar`: Java ライブラリや実行可能アプリケーション向けの JAR で、省略時の既定値
- `war`: Web アプリケーション向けの WAR
- `pom`: 親 POMや複数モジュールを束ねるプロジェクト

`packaging` に応じて、Maven がライフサイクルの各段階で実行する処理も変わります。  
単に拡張子を決める項目ではなく、プロジェクトのビルド方式を選ぶ項目だと考えます。  

## dependencies で必要なライブラリを宣言する

利用するライブラリは `dependencies` の中へ宣言します。  
次の例では、JUnit Jupiter をテストで利用します。  

```xml
<dependencies>
  <dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>5.11.0</version>
    <scope>test</scope>
  </dependency>
</dependencies>
```

Maven は座標を基にリポジトリから成果物を取得し、ローカルリポジトリへ保存します。  
一度取得した成果物は通常 `~/.m2/repository` から再利用されます。  
`scope` は、その依存関係をコンパイルやテストなどのどの場面で使うかを表し、[依存関係の管理](./dependencies) で詳しく扱います。  

## 基本的な pom.xml

次は、Java 17 で JAR を作るプロジェクトの基本的な POM です。  

```xml
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
                             https://maven.apache.org/xsd/maven-4.0.0.xsd">
  <modelVersion>4.0.0</modelVersion>

  <groupId>com.example</groupId>
  <artifactId>order-api</artifactId>
  <version>1.0.0-SNAPSHOT</version>
  <packaging>jar</packaging>

  <properties>
    <maven.compiler.release>17</maven.compiler.release>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
  </properties>

  <dependencies>
    <dependency>
      <groupId>org.junit.jupiter</groupId>
      <artifactId>junit-jupiter</artifactId>
      <version>5.11.0</version>
      <scope>test</scope>
    </dependency>
  </dependencies>
</project>
```

`modelVersion` は POM モデルの版で、Maven 3 系では通常 `4.0.0` を指定します。  
`properties` は値をまとめて定義する場所で、ここではコンパイル対象の Java リリースと文字コードを指定しています。  
`SNAPSHOT` が付いたバージョンは開発途中の版を表し、同じバージョン名でも内容が更新される可能性があります。  

標準的なディレクトリ構成は次のとおりです。  

```text
order-api/
├── pom.xml
└── src/
    ├── main/
    │   ├── java/
    │   └── resources/
    └── test/
        ├── java/
        └── resources/
```

この規約に従えば、ソースディレクトリを個別に設定しなくても Maven が読み取れます。  
変更も可能ですが、理由のない独自構成は設定を増やし、別のプロジェクトへ移ったときの理解を難しくします。  

<details>
<summary>実効 POM とは</summary>

実際のビルド設定は、現在の `pom.xml` だけで決まるとは限りません。  
親 POM、Maven の既定値、有効なプロファイルなどを統合した結果を「実効 POM」と呼びます。  
設定の出どころが分からないときは、後のページで扱う `mvn help:effective-pom` で確認できます。  
</details>

## よくあるつまずき

- `artifactId` だけで依存関係を識別できると考える
- Java の実行バージョンと、Maven がコンパイルに使うバージョンを混同する
- `SNAPSHOT` を固定されたリリース版と同じように扱う
- POM に依存関係を宣言せず、手作業で JAR をクラスパスへ追加する
- 標準ディレクトリ構成を変えた理由と設定を共有しない

## まとめ

- Maven は POM を使ってプロジェクト情報、依存関係、ビルド設定を共有する
- 成果物は `groupId`、`artifactId`、`version` の座標で識別する
- `packaging` は成果物の種類とビルド方式に関わる
- 規約に沿ったディレクトリ構成は、設定量と環境差を減らす
