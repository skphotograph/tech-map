# リファクタリングの道具箱

設計原則を理解しても、動いている大きなクラスを一度に書き直すのは危険です。  
リファクタリングは外から見た振る舞いを保ったまま内部構造を改善する活動で、小さな手順と確認を積み重ねます。  

## このページで分かること

- Extract Method、Extract Class、Sprout による安全な分割
- Value Object と DTO の役割の違い
- コンストラクタインジェクションと継承から委譲への切り替え
- Strategy、Factory、Template Method を導入する場面

## 先に安全網を作る

変更前に、現在の重要な振る舞いをテストで固定します。  
内部実装そのものではなく、入力に対する結果、状態変化、外部へ依頼する内容を確認します。  

十分なテストがない既存コードでは、代表的な正常系と壊したくない境界条件から Characterization Test（特性テスト）を追加します。  
これは現在の挙動を記録するテストで、現在の実装が理想的だと保証するものではありません。  

一回の変更を小さくし、コンパイルとテストを頻繁に実行します。  
構造変更と仕様変更を同時に行うと、失敗の原因を切り分けにくくなります。  

:::tip[リファクタリングの単位]

名前変更、抽出、依存の差し替えを一度に行わず、動作確認できる小さな変更へ分けます。  

:::

## Extract Method

Extract Method（メソッドの抽出）は、長い処理の一部へ目的を表す名前を付け、別メソッドへ移します。  

```java
void confirm(Order order) {
    validateConfirmable(order);
    order.confirm();
    repository.save(order);
}

private void validateConfirmable(Order order) {
    if (order.lines().isEmpty()) {
        throw new IllegalStateException("明細が必要です");
    }
}
```

コメントで「入力確認」「合計計算」と区切られている箇所や、同じ抽象度ではない細部が混ざる箇所は候補です。  
抽出後の名前が決まらない場合、処理の責務自体がまだ混ざっている可能性があります。  

引数が多すぎる、戻り値が複数必要になる場合は、関連するデータと振る舞いを別のオブジェクトへまとめる段階かもしれません。  

## Extract Class

Extract Class（クラスの抽出）は、異なる変更理由を持つフィールドとメソッドを新しいクラスへ移します。  
注文クラスが配送先の形式検証まで抱えているなら、`ShippingAddress` へ抽出できます。  

```java
record ShippingAddress(String postalCode, String city, String street) {
    ShippingAddress {
        if (postalCode == null || postalCode.isBlank()) {
            throw new IllegalArgumentException("郵便番号が必要です");
        }
    }
}
```

まず新しいクラスを作り、元のクラスから委譲し、呼び出し側を少しずつ移します。  
抽出直後に重複が一時的に残っても、各段階で動作を確認できることを優先します。  

## Sprout Method と Sprout Class

Sprout（芽を出す）は、テストしにくい既存コードを大きく変更せず、新しい処理をテスト可能なメソッドやクラスとして追加する方法です。  

たとえば巨大なバッチ処理へ新しい料金計算を追加する場合、計算を純粋な `ShippingFeeCalculator` として作り、既存処理から呼びます。  
既存コード全体を先に整理しなくても、新しい規則を独立してテストできます。  

Sprout は移行の足場です。  
同じ種類の処理が増えたら、周辺の責務も段階的に新しい境界へ移します。  

## Value Object へ置き換える

金額、メールアドレス、タスク ID などを `String` や `int` のまま扱うと、取り違えや検証の重複が起きます。  
規則と操作を持つ値を Value Object へ置き換えます。  

```java
record TaskId(UUID value) {
    TaskId {
        Objects.requireNonNull(value);
    }
}

record TaskTitle(String value) {
    TaskTitle {
        if (value == null || value.isBlank()) {
            throw new IllegalArgumentException("タイトルが必要です");
        }
        if (value.length() > 100) {
            throw new IllegalArgumentException("タイトルは 100 文字以内です");
        }
    }
}
```

まず生成箇所を見つけ、Value Object へ変換する境界を決めます。  
外部 API や永続化では文字列として扱い、アダプターで Value Object と相互変換できます。  

## DTO と Value Object の違い

DTO（Data Transfer Object）は、層やプロセスの境界を越えてデータを運ぶことが主な役割です。  
JSON の形、画面表示、外部 API の契約などに合わせて変化します。  

Value Object はドメインの値と規則を表し、値による等価性や意味のある操作を持ちます。  
DTO は転送先の都合、Value Object は業務上の意味が主な変更理由です。  

```java
record CreateTaskRequest(String title) {}

TaskTitle title = new TaskTitle(request.title());
```

同じ `record` 構文で書けても役割は異なります。  
入力 DTO の検証は「項目が存在し、形式を読めるか」、Value Object の検証は「業務上、有効な値か」というように境界を意識します。  

## コンストラクタインジェクション

クラスの内部で具体的な依存を生成すると、利用側は差し替えられず、テストでも実際の外部資源が必要になります。  

```java
final class TaskService {
    private final TaskRepository repository;
    private final Clock clock;

    TaskService(TaskRepository repository, Clock clock) {
        this.repository = Objects.requireNonNull(repository);
        this.clock = Objects.requireNonNull(clock);
    }
}
```

コンストラクタインジェクションでは、必要な依存が生成時に明示され、初期化後は `final` にできます。  
テストではメモリ実装や固定した `Clock` を渡せます。  

コンストラクタ引数が増えすぎた場合、DI の方式ではなくクラスの責務が多すぎる可能性を確認します。  

## 継承よりコンポジション

親クラスの実装を再利用するためだけの継承は、親の内部変更や初期化順序へ子クラスを結び付けます。  
コンポジションは必要な部品をフィールドとして保持し、処理を委譲します。  

```java
final class AuditedTaskService {
    private final TaskService tasks;
    private final AuditLog auditLog;

    AuditedTaskService(TaskService tasks, AuditLog auditLog) {
        this.tasks = tasks;
        this.auditLog = auditLog;
    }

    void complete(TaskId id) {
        tasks.complete(id);
        auditLog.record("task completed: " + id.value());
    }
}
```

コンポジションでは、必要な役割を組み合わせやすく、親クラスの公開・保護メンバーへ依存しません。  
ただし、明確な「is-a」関係があり、親型の契約を守れる場合まで継承を避ける必要はありません。  

## Strategy

Strategy は、交換可能なアルゴリズムや方針を共通の契約として分けるパターンです。  
条件分岐が複数箇所へ散らばる場合や、実行時に方針を選ぶ場合に役立ちます。  

```java
interface TaskPriorityPolicy {
    int priorityFor(Task task);
}

final class DueDatePriority implements TaskPriorityPolicy {
    private final Clock clock;

    DueDatePriority(Clock clock) {
        this.clock = clock;
    }

    @Override
    public int priorityFor(Task task) {
        return task.isOverdue(clock.instant()) ? 100 : 10;
    }
}
```

実装が一つで変化の兆候もない段階では、条件式のままの方が読みやすいことがあります。  
方針の追加頻度と、分岐が散らばる危険を見て導入します。  

## Factory

Factory は、オブジェクトの生成手順を利用側から分離します。  
複数の検証や部品の組み立てが必要なとき、名前付きの生成操作で意図を表せます。  

```java
final class OrderFactory {
    Order create(OrderRequest request) {
        Order order = new Order(OrderId.newId());
        request.lines().forEach(line ->
            order.addLine(line.productId(), line.unitPrice(), line.quantity()));
        return order;
    }
}
```

単純なコンストラクタ呼び出しを隠すだけなら、Factory が間接層を増やすだけになることもあります。  
生成規則、実装選択、外部データからの復元など、生成に独立した責務があるときに使います。  

## Template Method

Template Method は、処理の共通手順を親クラスで定義し、一部のステップを子クラスへ任せるパターンです。  

```java
abstract class TaskImporter {
    final List<Task> importTasks(Path path) {
        List<String> lines = readLines(path);
        return lines.stream().map(this::parse).toList();
    }

    protected abstract Task parse(String line);

    private List<String> readLines(Path path) {
        // 例示のため省略
        return List.of();
    }
}
```

処理順序を共通化し、差分だけをオーバーライドできます。  
ただし継承による結合が生まれ、実行時の組み替えは難しくなります。  
差分を Strategy として委譲する方が自然か、比較して選びます。

Mediator は、複数のオブジェクトが互いを直接知る代わりに、協調処理を仲介役へ集めるパターンです。  
画面上の多数の部品が相互に通知し合う場合や、複数コンポーネントの連携手順を一か所で調整したい場合に使えます。  

仲介役がすべての判断を抱えると巨大な Controller になりやすいため、各オブジェクト自身が持つべき規則まで移さないようにします。

## 段階的な改善例

大きな注文処理を改善するときは、次のように進められます。  

1. 現在の正常系と境界条件をテストで固定する
2. 金額計算を Extract Method し、名前で意図を表す
3. 金額と通貨を `Money` Value Object へ置き換える
4. 保存処理を `OrderRepository` へ Extract Class する
5. Repository をコンストラクタから受け取る
6. 割引の分岐が増えた段階で Strategy を導入する

各段階でテストを通し、レビュー可能な大きさを保ちます。  
最終形を一度に作るより、現在より少し安全な状態を連続して作る方が、既存の振る舞いを守りやすくなります。  

## よくあるつまずき

- テストを用意せず、大規模な移動と名前変更を同時に行う
- Extract Method 後も引数が多いままで、責務の混在を見逃す
- DTO と Value Object を同じものとして全層で共有する
- DI コンテナを使うこと自体を依存性注入と考え、内部で依存を生成する
- デザインパターンの名前を先に選び、変化のない箇所へ型を増やす

## まとめ

- リファクタリングは振る舞いを保ち、小さな変更とテストを繰り返す
- Extract Method、Extract Class、Sprout で既存コードから責務を段階的に分ける
- Value Object は意味と規則、DTO は境界を越えるデータを表す
- コンストラクタ DI とコンポジションで依存を明示し、Strategy などは実際の変化に合わせて使う
