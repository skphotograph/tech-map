# GRASP

クラスを分ける方針が決まっても、「注文自身が合計を計算するのか、注文サービスが計算するのか」で迷うことがあります。  
GRASP（General Responsibility Assignment Software Patterns）は、責務をどのオブジェクトへ割り当てるかを考える九つのパターンです。

## このページで分かること

- GRASP が設計で果たす役割
- Information Expert、Creator、Controller の基本
- 低結合、高凝集、ポリモーフィズムを責務配置に使う方法

## Information Expert

Information Expert（情報エキスパート）は、必要な情報を持つオブジェクトへ責務を置く考え方です。  
注文合計に明細の単価と数量が必要なら、それらを持つ `OrderLine` と `Order` が計算を担当する候補になります。

```java
record OrderLine(int unitPrice, int quantity) {
    int subtotal() {
        return unitPrice * quantity;
    }
}

final class Order {
    private final List<OrderLine> lines;

    int totalAmount() {
        return lines.stream()
            .mapToInt(OrderLine::subtotal)
            .sum();
    }
}
```

呼び出し側が内部データを取り出して計算するより、規則が散らばりにくくなります。  
ただし、保存や通知など外部技術を必要とする責務まで、情報を持つドメインオブジェクトへ詰め込む必要はありません。

## Creator

Creator（生成者）は、あるオブジェクトを誰が生成するかを決める手掛かりです。  
次の関係が強いクラスを生成者の候補にします。

- 生成されるオブジェクトを集約または保持する
- 生成されるオブジェクトを頻繁に利用する
- 生成に必要な初期データを持つ

`Order` が `OrderLine` を保持し、追加時の規則も守るなら、`order.addLine(product, quantity)` のように生成を注文へ任せる構造が考えられます。  
生成手順が複雑な場合は、Factory へ責務を移すこともあります。

## Controller

Controller は、画面や API から届いたシステム操作を最初に受ける、UI ではないオブジェクトです。  
注文登録なら `PlaceOrder` のようにユースケースを表すクラスが候補になります。

Controller は入力を受け、処理を適切なオブジェクトへ委譲します。  
すべての業務判断を Controller 自身へ書くと肥大化するため、流れの調整と業務規則を分けます。

```java
final class PlaceOrder {
    private final OrderRepository repository;

    OrderId execute(PlaceOrderCommand command) {
        Order order = Order.create(command.lines());
        repository.save(order);
        return order.id();
    }
}
```

## Low Coupling と High Cohesion

Low Coupling（低結合）は変更の波及を抑え、High Cohesion（高凝集）は関連する責務をまとめます。  
ほかの GRASP パターンを選ぶときも、この二つが評価軸になります。

責務を移した結果、ひとつのクラスが多くの詳細を知るなら結合が強すぎるかもしれません。  
反対に、ひとつの目的を達成する処理が多数の小さなクラスへ散らばり、単独では意味を持たないなら凝集度を見直します。

## Polymorphism

種類によって振る舞いが変わるとき、条件分岐を一か所へ増やし続ける代わりに、共通の契約へ振る舞いを割り当てます。

```java
interface NotificationChannel {
    void send(String message);
}
```

メールやアプリ内通知はそれぞれ `send` を実装し、利用側は具体的な種類を判定しません。  
種類が固定され、分岐が一か所だけなら、無理に型を増やさない判断もあります。

<details>
<summary>Pure Fabrication</summary>

Pure Fabrication（純粋架空物）は、業務概念には直接対応しないクラスを作り、低結合や高凝集を実現するパターンです。  
たとえば永続化を担当する Repository は、業務上の物ではなくても、保存の詳細を分離する役割を持ちます。
</details>

<details>
<summary>Indirection</summary>

Indirection（間接化）は、二つの要素の間に別の要素を置き、直接の結合を弱めます。  
外部通知 API とユースケースの間に `NotificationChannel` を置く例が該当します。  
間接層を増やすほど追跡コストも増えるため、隔離したい変化がある場所で使います。
</details>

<details>
<summary>Protected Variations</summary>

Protected Variations（変動からの保護）は、変化しやすい箇所を見つけ、安定したインタフェースの後ろへ隠します。  
保存方式や外部サービスの仕様をポートの後ろへ置く設計が例です。  
予想だけで保護範囲を広げず、実際の変化や高い変更費用を根拠にします。
</details>

## GRASP を使う手順

1. 実現したい操作と、必要な情報を挙げる
2. Information Expert と Creator から自然な候補を探す
3. Controller が処理を抱えず、適切に委譲しているか確認する
4. 低結合、高凝集、ポリモーフィズムで候補を比較する
5. 技術的な責務には Pure Fabrication や Indirection を検討する

九つの名前をすべてコードへ登場させる必要はありません。  
責務の置き場所を説明し、別案と比較するための語彙として使います。

## まとめ

- GRASP は、責務をどのオブジェクトへ割り当てるかを考えるパターン群
- 情報を持つ相手へ判断を任せ、Controller は処理の調整に集中させる
- 低結合と高凝集を評価軸にし、必要な箇所だけ間接化する
