# 設計の入口

動くコードを書けても、機能追加のたびに同じ修正が何か所にも広がったり、ひとつのクラスを直すだけで別の機能まで壊れたりすることがあります。  
設計は見栄えのよいクラス図を作る作業ではなく、変更の影響を予測しやすくするための判断です。

## この章で分かること

- オブジェクト指向と代表的な設計原則を、目的から説明できる
- 責務と依存関係を整理し、変更理由の異なるコードを分けられる
- レイヤード、ヘキサゴナル、DDD などの関係と使いどころを見渡せる
- 小さなリファクタリングから設計を改善できる

## 設計は「変更のしやすさ」を扱う

注文の割引規則、保存先、画面表示が同じクラスに詰め込まれていると、変更理由の異なるものが一緒に動きます。  
一方、細かく分ければ必ずよいわけでもありません。  
分割しすぎると処理を追うために多くのファイルを往復することになります。

この章では、原則を絶対的な規則として暗記するのではなく、どの変更を局所化したいのかを考える材料として扱います。

:::tip[設計を考える問い]

「このコードは何を知り、何に責任を持ち、どの変更で一緒に変わるか」を確認します。

:::

目の前の変更で困っている点に近いページから戻って読む使い方もできます。

## 原則同士の関係

DRY や SOLID はコードの判断を助け、GRASP は責務の置き場所を考える語彙を与えます。  
レイヤードやヘキサゴナルは、より大きな単位で依存関係を整理します。  
DDD は業務知識をモデルへ反映する考え方であり、特定のアーキテクチャを必須にはしません。

原則の名前が違っても、「関心を分ける」「安定させたいものへ依存を向ける」という狙いは重なります。  
名前を増やすことより、変更時の判断に使えることが大切です。

## まとめ

- 設計の目的は、変更の影響を予測しやすくすること
- 原則は採用数を競うものではなく、判断を説明するための道具
- クラス内の責務からシステム境界まで、段階的に視野を広げる
