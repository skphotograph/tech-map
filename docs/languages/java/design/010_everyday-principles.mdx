# 日常で使う設計原則

重複をなくそうとして共通化したのに、片方だけ仕様を変えたくなって分岐だらけになることがあります。  
設計原則は短い標語だけで適用すると、別の問題を作りかねません。  
ここでは DRY、KISS、YAGNI と、凝集度、結合度、デメテルの法則を、判断の観点として整理します。

## このページで分かること

- DRY、KISS、YAGNI が防ごうとしている問題
- 凝集度を高め、結合度を下げる意味
- デメテルの法則（LoD）で長い依存の連鎖を見直す方法

## DRY: 知識の重複を避ける

DRY（Don't Repeat Yourself）は、同じ見た目のコードをすべて一つにする原則ではありません。  
ひとつの規則を変更するときに複数箇所を直さなければならない、**知識の重複**を避けます。

```java
final class ShippingFee {
    static final int FREE_SHIPPING_THRESHOLD = 5_000;

    int calculate(int orderAmount) {
        return orderAmount >= FREE_SHIPPING_THRESHOLD ? 0 : 500;
    }
}
```

送料無料の基準が画面表示と注文計算へ別々に埋め込まれているなら、ひとつの規則として集約する価値があります。  
反対に、たまたま同じ式でも変更理由が違うものをまとめると、将来の変更で不自然な引数や分岐が増えます。

:::tip[重複をまとめる基準]

コードが似ているかではなく、同じ理由で同時に変わる知識かを確認します。

:::

## KISS: 理解できる小さな解決を選ぶ

KISS（Keep It Simple, Stupid）は、機能を雑に作ることではありません。  
要件を満たす候補の中から、読み手が挙動を予測しやすい構造を選ぶ考え方です。

割引方針がひとつしかない段階で、設定ファイル、リフレクション、独自ルールエンジンまで導入すると、変更点より仕組みの理解に時間がかかります。  
まず明示的な条件分岐や小さなクラスで表現し、変化の軸が見えてから抽象化しても遅くありません。

「短いコード」と「単純な設計」は同じではありません。  
複雑な規則を一行へ詰め込むより、名前の付いた中間結果へ分けた方が理解しやすいことがあります。

## YAGNI: 必要になるまで作らない

YAGNI（You Aren't Gonna Need It）は、将来を一切考えないという意味ではありません。  
根拠のない将来要件を先回りして実装し、現在のコードへ維持コストを持ち込まないという判断です。

「いつか保存先が十種類になるかもしれない」という予想だけで拡張機構を作るより、現在必要な契約を小さく保ちます。  
ただし、セキュリティ、データ移行、外部公開 API の互換性など、後から直す費用が大きい事項は早めに検討します。

<details>
<summary>YAGNI と拡張性は両立できる</summary>

先回りした機能を実装しなくても、責務を分け、テストを用意し、変更しやすい名前を付けることはできます。  
「今は実装しない」と「将来変更できない形にする」は別の判断です。
</details>

## 凝集度: 一緒に置く理由の強さ

凝集度は、ひとつのモジュール内の要素がどれだけ同じ目的に関係しているかを表します。  
注文の合計計算と確定可否の判断は注文の規則としてまとまりやすい一方、メール送信や SQL 文字列の組み立ては変更理由が異なります。

```java
final class Order {
    private final List<OrderLine> lines;

    int totalAmount() {
        return lines.stream()
            .mapToInt(OrderLine::subtotal)
            .sum();
    }
}

record OrderLine(int unitPrice, int quantity) {
    int subtotal() {
        return unitPrice * quantity;
    }
}
```

高凝集なクラスは、「このクラスは何をするものか」を短く説明しやすくなります。  
クラス名に `Manager` や `Utils` を付けないとまとめにくい場合は、複数の責務が混ざっていないか確認します。

## 結合度: 変更が伝わる強さ

結合度は、モジュール同士がどれだけ強く依存しているかを表します。  
具体的なクラス、内部データ構造、呼び出し順序を多く知るほど、片方の変更がもう片方へ伝わりやすくなります。

低結合を目指す方法には、次のようなものがあります。

- 必要な操作だけを表す小さなインタフェースへ依存する
- オブジェクトの内部コレクションを直接公開しない
- 生成と利用を分け、依存する部品をコンストラクタから受け取る
- 境界をまたぐデータ形式を明示する

依存をゼロにはできません。  
低結合の目的は、意味のある協調を残しながら、変更の波及を制御することです。

## デメテルの法則: 直接の相手と話す

デメテルの法則（Law of Demeter、LoD）は、「最小知識の原則」とも呼ばれます。  
オブジェクトが、直接受け取った相手の内部構造をたどりすぎないようにします。

```java
// 内部構造を何段も知っている
String city = order.customer().address().city();
```

このコードは、注文、顧客、住所の構造すべてに依存します。  
呼び出し側が本当に必要としている問いを、適切なオブジェクトへ置けないか考えます。

```java
boolean domestic = order.isDomestic(destinationCountry);
```

ただし、DTO や不変なデータ構造から表示用の値を読むだけなら、連鎖が直ちに問題とは限りません。  
メソッド呼び出しの個数を機械的に数えるのではなく、相手の内部構造を知りすぎて変更に弱くなっているかを見ます。

## 原則が衝突したとき

DRY のための共通化が KISS に反して分かりにくくなることがあります。  
また、低結合を目指してインタフェースを増やしすぎると、処理の追跡が難しくなります。

その場合は、現在予想される変更、間違えた場合の修正費用、読み手が追う範囲を比較します。  
原則名だけで結論を出さず、どの問題を減らすための選択かをレビューで説明します。

## よくあるつまずき

- 数行似ているだけで共通化し、異なる変更理由を結び付ける
- 「将来使うかもしれない」設定項目や抽象クラスを先に増やす
- クラス数を減らすことを単純さと考え、ひとつのクラスへ責務を集める
- 低結合を依存関係がないことと誤解する

## まとめ

- DRY は知識の重複、KISS は理解しにくい複雑さ、YAGNI は根拠のない先行実装を避ける
- 高凝集は同じ目的の要素をまとめ、低結合は変更の波及を抑える
- LoD は、相手の内部構造をたどる依存を見直す手掛かりになる
