# ロックファイルとインストール

同じ `package.json` を使ったのに、昨日の端末と今日の CI で入る依存関係が違う。  
許容範囲の中で新しい版が選ばれると、このような差が起こり得ます。  
`package-lock.json` は、実際に解決した依存関係を記録し、インストールを再現しやすくします。

## このページで分かること

- バージョン範囲と実際に入るバージョンの違い
- `package-lock.json` をコミットする理由
- `npm install` と `npm ci` の使い分け
- 依存関係を安全に更新する流れ

## package.json は希望、ロックファイルは解決結果

`package.json` の依存関係には、利用を許容するバージョン範囲が書かれます。

```json
{
  "dependencies": {
    "example-library": "^2.3.1"
  }
}
```

一方、`package-lock.json` には、npm が選んだ正確なバージョンや、そのパッケージがさらに必要とする依存関係が記録されます。  
直接追加していない依存関係も含め、インストール全体の解決結果を固定するファイルです。

:::tip[ロックファイルもコミットする]

アプリケーションでは `package.json` と `package-lock.json` を一緒に Git へコミットし、開発端末と CI が同じ解決結果を使えるようにします。

:::

ロックファイルを「自動生成だから不要」と削除すると、インストールのたびに新しいバージョンが選ばれる余地が増えます。  
手で編集せず、npm のコマンドで更新します。

## `npm install` で依存関係をそろえる

リポジトリを取得したあと、`package.json` があるディレクトリで実行します。

```bash
npm install
```

成功時には追加・変更されたパッケージ数と監査結果が表示され、`node_modules` が作られます。

```text
added 12 packages, and audited 13 packages in 1s

found 0 vulnerabilities
```

`added 12 packages` は今回追加された数、`audited 13 packages` は確認対象の数です。  
実際の数や監査結果はプロジェクトと実行時点で変わります。

`npm install` はロックファイルを参照しつつ、依存関係の追加や変更に合わせてロックファイルを更新できます。  
開発中にパッケージを追加・更新する場面で使います。

## `npm ci` で固定された内容を入れる

CI や、取得直後の状態を厳密に再現したい環境では次を使います。

```bash
npm ci
```

`npm ci` には次の特徴があります。

- `package-lock.json` が必要
- `package.json` とロックファイルが食い違うと失敗する
- 既存の `node_modules` を削除してからインストールする
- ロックファイルを書き換えない

成功時の出力は `npm install` と似ています。  
重要なのは、固定された解決結果から外れた場合に黙って調整せず、失敗として知らせる点です。

| 場面                             | コマンド      |
| -------------------------------- | ------------- |
| 依存関係を追加・更新する開発作業 | `npm install` |
| ロック済みの内容を CI などで再現 | `npm ci`      |

## バージョン範囲の `^` と `~`

Semantic Versioning では、バージョンを主に `メジャー.マイナー.パッチ` で表します。  
たとえば `2.3.1` なら、`2` がメジャー、`3` がマイナー、`1` がパッチです。

- `^2.3.1`：通常は `2.x.x` の範囲で更新を許容する
- `~2.3.1`：通常は `2.3.x` の範囲で更新を許容する
- `2.3.1`：そのバージョンだけを指定する

`^` や `~` は互換性を保証する記号ではなく、許容する範囲を表します。  
更新後はテストを実行し、変更内容も確認します。

<details>
<summary>0.x 系の ^ は範囲が狭い</summary>

`^0.3.1` のようにメジャーバージョンが `0` の場合、通常は `0.3.x` の範囲が対象です。  
外部から利用される機能がまだ安定していない版として扱われるため、`^2.3.1` より更新範囲が狭くなります。

</details>

## 依存関係を更新する流れ

更新はロックファイルだけを無条件に作り直すのではなく、差分を確認できる単位で進めます。

1. 更新対象とリリースノートを確認する
2. `npm install <パッケージ名>@<バージョン>` で更新する
3. `package.json` と `package-lock.json` の差分を確認する
4. `npm run test` など、プロジェクトの確認用 script を実行する
5. ふたつのファイルを一緒にコミットする

セキュリティ警告が表示されても、内容を確認せずに破壊的な更新を適用するのは避けます。  
影響するパッケージと修正版を確認し、テストできる状態で更新します。

## よくあるつまずき

- `package-lock.json` を Git の対象外にする
- ロックファイルを手で編集する
- CI で毎回異なる解決を許し、失敗を再現しにくくする
- `^` や `~` が互換性を保証すると考え、更新後のテストを省く
- `node_modules` をコミットする

## まとめ / 次に学ぶとよいこと

- `package.json` は許容範囲、`package-lock.json` は解決された依存関係を記録する
- アプリケーションではロックファイルをコミットする
- 開発中の追加・更新には `npm install`、固定した再現には `npm ci` を使う
- バージョン範囲内の更新でも、差分確認とテストが必要
