# ツールによる型チェック

型ヒントを書いても、確認を個人のエディタ設定だけに頼ると基準がそろいません。  
静的型チェッカーを共通コマンドにすると、実行前に同じ基準で食い違いを探せます。  

## このページで分かること

- mypy と Pyright の役割
- mypy の導入と実行
- `pyproject.toml` で設定を共有する方法
- 型エラーへ段階的に対応する考え方

## チェッカーを実行する

mypy と Pyright は、コードを実行せず型の整合性を調べます。  
既存プロジェクトの設定に合わせ、チームで基準となる一つを選びます。ここでは mypy を使います。  
次のコマンドは、プロジェクト用の仮想環境を有効にした状態で実行します。これにより、アプリと同じ環境へチェッカーを導入できます。  

```bash
python -m pip install mypy
python -m mypy src
```

成功時の代表的な出力です。  

```text
Success: no issues found in 1 source file
```

問題がある場合は、ファイル、行、内容、期待した型、エラーコードが表示されます。  

```text
src/main.py:5: error: Argument 1 has incompatible type "int"; expected "str"  [arg-type]
```

注釈と実装のどちらが仕様に合うかを確認し、正しい側へそろえます。

## 設定を共有する

```toml title="pyproject.toml"
[tool.mypy]
python_version = "3.11"
files = ["src", "tests"]
check_untyped_defs = true
warn_unused_ignores = true
```

設定後は `python -m mypy` で共通の対象を確認できます。  
README と CI でも同じコマンドを使うと、レビュー前に同じ問題を見つけられます。  

:::tip[段階的に対象を広げる]

既存コードでは、公開 API や新しく変更する範囲から注釈を増やします。警告を解消しながら対象を広げると、重要な問題が大量の警告に埋もれません。  

:::

`# type: ignore` は、型情報が不足するなど理由を確認した箇所だけに使います。  
可能なら `# type: ignore[arg-type]` のようにコードを限定し、不要になった抑制を検出できるようにします。  

## よくあるつまずき

- mypy と Pyright を設定なしで混在させ、端末ごとに結果を変える
- 仮想環境の外へ mypy を入れ、プロジェクトと異なる Python や依存を調べる
- 型エラーの意味を確認せず、注釈を実装へ合わせるだけで仕様を変える
- 理由のない `# type: ignore` で、後から見つかる不一致まで隠す
- エディタだけで確認し、README や CI に共通コマンドを残さない

## まとめ

- mypy と Pyright は型の食い違いを実行前に調べる
- チェッカー、設定、実行コマンドをチームでそろえる
- エラーは仕様を確認してから実装または注釈を直す
- 既存コードには段階的に適用する
