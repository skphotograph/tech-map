# 型ヒントが必要な理由

辞書だと思って受け取った値がリストだった。  
文字列を返す関数だと思ってつないだら、一部の経路だけ `None` が返った。  
型ヒントは、こうした **データの形の食い違い** を実行前に見つけるための手がかりです。

## このページで分かること

- 型ヒントがコードの読み書きをどう助けるか
- 実行時エラーと静的型チェックの違い
- 型注釈が実行時には強制されないこと

## 入力と出力の約束を書く

次の関数は、文字列を受け取り、文字列を返すことを注釈で表しています。

```python
def greeting(name: str) -> str:
    return f"Hello, {name}"


message = greeting("Aiko")
print(message)
```

実行結果です。

```text
Hello, Aiko
```

`name: str` は引数の期待する型、`-> str` は返り値の期待する型です。  
呼び出す側は実装をすべて読まなくても、関数の境界を把握できます。

## 実行前に食い違いを探す

Python は、プログラムを動かして値を扱うときに型を確認する **動的型付け** の言語です。  
これに対し、コードを実行せず注釈から型の食い違いを調べることを **静的型チェック** と呼びます。

注釈と異なる値を渡したコードを考えます。

```python
def double(value: int) -> int:
    return value * 2


result = double("3")
```

Python 自体はこの呼び出しを禁止せず、実行結果は文字列 `"33"` になります。  
一方、静的型チェッカーは「`int` を期待する引数へ `str` を渡している」と報告できます。

```text
Argument 1 to "double" has incompatible type "str"; expected "int"
```

TypeScript の型チェックと同じく、すべての障害を防ぐものではありません。  
それでも、実行経路に入る前に形の不一致を見つけられるため、修正範囲を狭めやすくなります。

:::tip[境界から型を付ける]

最初から全変数へ注釈を書く必要はありません。関数の引数と返り値、共有するデータ構造など、利用者との境界から始めると効果が見えやすくなります。

:::

## 型ヒントが役立つ場面

- 関数の使い方をエディタの補完で確認する
- リファクタリングで古い呼び出し方を探す
- レビューで `None` や辞書のキー漏れに気づく
- ライブラリの公開 API を利用者へ伝える

**リファクタリング** は、外から見える振る舞いを保ったままコードの構造を整理することです。  
関数名や引数を変えたとき、型チェッカーが古い呼び出し方を報告すれば、直す場所を探しやすくなります。

実行時に外部入力を検証することは、型ヒントとは別の責務です。  
HTTP やファイルから受け取った値は、型注釈があっても形式・範囲・必須項目を実行時に確認します。

## まとめ

- 型ヒントはデータの形をコード上の約束として共有する
- 静的型チェックは、実行前に形の食い違いを探す
- 型注釈だけでは通常、実行時の値を検証しない
