# アプリケーションの見取り図

入力、計算、通信、表示を一つの関数へ詰めると、変更の影響を追いにくくなります。  
まず入力・処理・出力で流れを捉え、変化しやすい外部境界を分けましょう。

## このページで分かること

- 入力・処理・出力という基本の流れ
- 外部との境界を分ける理由
- 副作用と中心の計算の違い
- 例外を意味のある形へ変換する方法

## 流れを三つに分ける

1. **入力**: HTTP、コマンドライン、ファイルから値を受け取る
2. **処理**: 値を検証し、計算や判断をする
3. **出力**: レスポンス、画面、ファイルへ結果を返す

```python
def discounted_price(price: int, rate: float) -> int:
    if price < 0:
        raise ValueError("price must be non-negative")
    if not 0 <= rate <= 1:
        raise ValueError("rate must be between 0 and 1")
    return int(price * (1 - rate))

print(discounted_price(2000, 0.1))
```

実行結果は `1800` です。  
HTTP とファイルのどちらから入力しても、この計算自体は変わりません。

## 副作用を境界へ寄せる

ネットワークから値を受け取る、ファイルへ書く、現在時刻を読むなど、関数の外にある状態へ触れることを **副作用** と呼びます。  
同じ入力なら同じ結果を返す計算と分けると、通信なしで確認できる範囲が増えます。

外部ライブラリの低レベルな例外は、必要に応じてアプリケーションが判断できる例外へ変換します。

```python
class UserNotFoundError(Exception):
    pass

def require_user(user_id: str, users: dict[str, str]) -> str:
    try:
        return users[user_id]
    except KeyError as error:
        raise UserNotFoundError(user_id) from error
```

`raise ... from error` は意味のある例外を渡しつつ、元の原因を調査できる形で残します。

:::tip[中心を外部の詳細から離す]

通信やファイル形式を知るコードを境界へ寄せると、中心の計算を小さくテストでき、外部手段の変更も局所化できます。

:::

## よくあるつまずき

- 入力、通信、計算、表示を一つの関数へ詰め、変更理由を分けられなくする
- 外部ライブラリの例外をどこでも直接扱い、中心の処理を通信方式へ結び付ける
- 小さな処理まで細かく分割し、値の流れをかえって追いにくくする
- 外部入力の検証と、型ヒントによる静的な確認を同じものだと考える

## まとめ

- アプリケーションは入力・処理・出力で見られる
- 副作用を中心の計算から分ける
- 外部の失敗をアプリケーションが扱える形へ変換する
- 分割は変更とテストの境界が明確になる範囲で行う
