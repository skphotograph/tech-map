# テストの基本

手で一度動かすだけでは、境界値や失敗時の確認が抜けやすくなります。  
自動テストは入力と期待する結果をコードに残し、変更後も同じ振る舞いを確認します。

## このページで分かること

- `unittest` で成功と例外を確認する方法
- テストケースを選ぶ基準
- 外部依存を差し替える理由

## 最初のテスト

```python title="pricing.py"
def discounted_price(price: int, rate: float) -> int:
    if price < 0:
        raise ValueError("price must be non-negative")
    return int(price * (1 - rate))
```

```python title="tests/test_pricing.py"
import unittest

from pricing import discounted_price

class DiscountedPriceTest(unittest.TestCase):
    def test_applies_discount(self) -> None:
        self.assertEqual(discounted_price(2000, 0.1), 1800)

    def test_rejects_negative_price(self) -> None:
        with self.assertRaises(ValueError):
            discounted_price(-1, 0.1)
```

```bash
python -m unittest discover -s tests
```

成功時は実行件数に続いて `OK` と表示されます。

```text
..
----------------------------------------------------------------------
Ran 2 tests in 0.001s

OK
```

先頭の `..` は二件のテストが成功したこと、`OK` は失敗がなかったことを表します。実行時間は環境によって変わります。  
代表的な正常値、境界値、空の値、不正値、過去に障害となった入力からケースを選びます。

## 外部依存を差し替える

実際の API を毎回呼ぶテストは、通信状態や外部データで結果が揺れます。  
外部から値を得る関数を引数で受け取ると、テスト用実装へ差し替えられます。

```python
from collections.abc import Callable

def calculate_total(
    order_id: str,
    load_order: Callable[[str], dict[str, int]],
) -> int:
    order = load_order(order_id)
    return order["unit_price"] * order["quantity"]
```

```python
def test_calculate_total(self) -> None:
    def fake_load_order(order_id: str) -> dict[str, int]:
        return {"unit_price": 1200, "quantity": 2}

    self.assertEqual(
        calculate_total("ORD-1001", fake_load_order),
        2400,
    )
```

:::tip[振る舞いを確認する]

内部の呼び出し回数だけに依存せず、入力に対する結果や例外を中心に確認すると、内部整理で壊れにくいテストになります。

:::

## よくあるつまずき

- 正常な一例だけをテストし、境界値や例外を確認しない
- テストをプロジェクトのルート以外から実行し、対象モジュールを読み込めなくする
- 実際の外部 API を呼び、通信状態によって結果が変わるテストにする
- 実装内部の細かな手順だけを固定し、整理しただけでテストを壊す
- 失敗したテストを削除して、期待する振る舞いまで失う

## まとめ

- 自動テストは期待する振る舞いをコードに残す
- 正常値、境界値、失敗を小さなケースに分ける
- `assertEqual` は結果、`assertRaises` は例外を確認する
- 外部依存を差し替えて中心の処理を安定してテストする
