# 再現可能なインストール

同じ依存条件でも、インストールした日によって推移的依存の版が変わることがあります。  
開発端末と CI をそろえるには、許容範囲に加えて解決されたバージョンを共有します。  

## このページで分かること

- 依存条件とロックファイルの違い
- 固定内容を更新・導入する流れ
- `requirements.txt` を使う構成
- 空の環境で再現性を確かめる方法

## 宣言と固定の役割

`pyproject.toml` は必要な直接依存と互換性のある範囲を宣言します。  
ロックファイルは、そこから選ばれた直接依存・推移的依存の具体的な版を記録します。  

ロックファイルの名前と操作は管理ツールごとに異なります。  
標準の pip には、すべてのプロジェクトで共通して使うロックファイルがありません。  
既存のロックファイルがあれば別形式を加えず、そのプロジェクトの手順を使います。  

## 更新と導入を分ける

1. 直接依存の宣言を変更する
2. 管理ツールでロックファイルを更新する
3. テストと型チェックを実行する
4. 宣言とロックの差分を一緒にレビューする
5. CI ではロック内容を変更せず導入する

更新時だけ依存の選び直しを許し、通常の開発や CI では記録済みの版を導入します。  
この二つを分けることで、関係のない作業中に依存が勝手に変わることを防げます。

## requirements.txt を使う構成

pip 中心の既存プロジェクトでは、固定一覧を使うこともあります。  

```text title="requirements.txt"
httpx==0.27.2
```

```bash
python -m pip install --requirement requirements.txt
```

成功時は `Successfully installed`、導入済みなら `Requirement already satisfied` と表示されます。  
`pip freeze` は環境内の全パッケージを出すため、調査用の依存まで含むことがあります。プロジェクトの生成手順を使ってください。  

`requirements.txt` という名前だけでは、手書きの直接依存一覧か、ツールが生成した固定一覧かは判断できません。  
先頭のコメントや README を確認し、生成物なら直接編集せず、元の宣言を直して再生成します。  

:::tip[空の環境で確かめる]

新しい仮想環境へ固定内容から導入し、README の手順だけでテストと型チェックが通ることを確認します。  

:::

依存更新ではロック内の推移的依存の差分も確認し、大きな更新はリリースノートと互換性を確認して進めます。  

## よくあるつまずき

- `pyproject.toml` の条件だけを共有し、端末ごとに異なる推移的依存を導入する
- 通常のインストール時にもロックを更新し、意図しない差分を混ぜる
- 用途の分からない環境で `pip freeze` し、不要なパッケージまで固定する
- 生成された固定一覧を手で直し、元の依存宣言と食い違わせる
- 既存プロジェクトへ別のロック方式を追加し、正しい手順を二つにする

## まとめ

- 依存条件は許容範囲、ロックは具体的な依存グラフを表す
- ロックの更新と固定内容の導入を分ける
- 固定一覧の生成方法も共有する
- 空の環境から導入して再現性を確認する
