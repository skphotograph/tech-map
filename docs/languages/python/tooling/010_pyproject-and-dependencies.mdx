# pyproject.toml と依存関係

仮想環境の中身だけでは、必要なパッケージと一時的に入れたものを区別できません。  
`pyproject.toml` にプロジェクト情報と直接依存を書き、コードと一緒に共有します。

## このページで分かること

- `pyproject.toml` の役割
- Python の条件と依存関係の書き方
- 直接依存と推移的依存の違い
- 実行用と開発用を分ける考え方

## プロジェクト情報を書く

`pyproject.toml` は、Python プロジェクトの名前、対応バージョン、依存関係、ビルド方法、各種ツール設定を一か所へまとめる標準的な設定ファイルです。  
仮想環境そのものは共有しないため、このファイルが「何を導入すれば動くか」を伝える設計図になります。

```toml title="pyproject.toml"
[build-system]
requires = ["setuptools"]
build-backend = "setuptools.build_meta"

[project]
name = "sample-client"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = [
  "httpx>=0.27,<1",
]
```

`requires-python` は対応する Python、`dependencies` は実行時に直接必要なパッケージです。  
`[build-system]` は、このプロジェクトをインストール可能な形へ組み立てる道具を pip に伝えます。  
標準の pip を使う構成では、次のようにプロジェクトと依存を導入できます。

```bash
python -m pip install .
```

開発中にソース変更をすぐ反映する構成では `python -m pip install --editable .` を使います。  
`--editable` は、インストール後も作業ディレクトリのソース変更を反映する開発向けの導入方法です。  
ビルド設定やコマンドは採用ツールで異なるため、既存プロジェクトでは README と `[build-system]` を確認します。

## 直接依存と推移的依存

自分のコードが直接 `import` するパッケージは直接依存に書きます。  
そのパッケージが内部で使うものは推移的依存で、インストール時に解決されます。推移的依存を自分でも直接使い始めたら、直接依存へ加えます。

## 開発用の依存

テスト、型チェック、整形は、配置先での実行には不要な場合があります。  
これらを実行用の依存と分けると、配置先へ不要な道具を入れずに済み、何のための依存かも判断しやすくなります。  
開発用依存の表し方と導入コマンドは管理ツールによって異なるため、既存の `pyproject.toml` と README にある方式へ合わせます。

:::tip[条件には理由を持つ]

下限は必要な機能や修正、上限は互換性の境界を基準にします。根拠なく広い条件や更新できない固定を直接依存へ並べないようにします。

:::

## よくあるつまずき

- 仮想環境へ入れただけで `pyproject.toml` を更新しない
- 直接使うパッケージを推移的依存に頼る
- `[project]` だけを書き、インストールに必要な `[build-system]` を確認しない
- 既存の管理ツールを確認せず別形式を追加する

## まとめ

- `pyproject.toml` はプロジェクト情報と依存関係の中心になる
- 実行時に直接必要なものを `dependencies` へ書く
- 推移的依存は直接依存から解決される
- 開発用依存は採用ツールの方式で分ける

次は [再現可能なインストール](./reproducible-installs) で、解決されたバージョンを共有します。
