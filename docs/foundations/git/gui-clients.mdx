# GUI で操作するとき

ターミナルのコマンドより、画面のボタンの方が楽に感じることは多いです。  
[GitHub Desktop](https://desktop.github.com/) や、VS Code / Cursor の Git パネル（ソース管理ビュー）は、その代表例です。

ただしこの教材では、**コマンドの意味を理解したうえで GUI を使う** ことを推奨します。  
「楽だから GUI だけ」だと、履歴が読みにくくなったり、困ったときに自分で立て直せなくなったりします。

:::warning[先に押さえること]

GUI は時短のための道具です。  
ボタンを押す前に、「これは `add` 相当か、`commit` 相当か」を言える状態を目指しましょう。

:::

## このページで分かること

- GUI がうれしい点と、GUI だけに頼るリスク
- 画面の操作が、どの Git の概念に対応するか
- GitHub Desktop / エディタの Git パネルの使い分けの目安

## なぜ GUI だけだと危ういか

GUI は「いま何をしたか」が画面上では分かりやすい一方、裏でどのコマンド相当が走ったかは見えにくいことがあります。  
その結果、次のようなことが起きやすくなります。

- コミットの粒度が雑になり、履歴の可読性が下がる
- ステージに載せたくないファイルまでまとめてコミットする
- 取り込み方（通常の merge と Squash and merge など）を、意味が分からないまま選ぶ
- エラーやコンフリクトのときに、画面の赤表示以外の手がかりが取れない

コマンドを一度追っていると、「このボタンは `git add` 相当」「これは `git commit` 相当」と対応づけられます。  
そうなってから GUI に移ると、速さも安全性も両立しやすいです。

## 先に押さえておきたい対応関係

| 画面でよくある操作             | 対応する考え方 / コマンド              |
| ------------------------------ | -------------------------------------- |
| 変更一覧を見る                 | [git status](./daily-commands)         |
| 差分を見る                     | [git diff](./daily-commands)           |
| コミットに含めるファイルを選ぶ | [ステージ / git add](./concepts)       |
| メッセージを書いて記録する     | [git commit](./setup-and-first-commit) |
| 履歴を見る                     | [git log](./daily-commands)            |
| ブランチを切り替える / 作る    | [ブランチ](./branch)                   |
| 取得・送信する                 | [git pull / git push](./remote)        |

GUI を使うときも、コミット前に差分を見る・意図の単位で残す、という [日常の操作](./daily-commands) の感覚はそのまま持っていってください。

## GitHub Desktop

GitHub 公式のデスクトップアプリです。  
リポジトリの clone、変更の確認、コミット、ブランチ切替、Pull Request の作成など、GitHub 連携まで一通り触れます。

向いている場面:

- GitHub 上のリポジトリを中心に作業する
- 差分や履歴を、ターミナルより視覚的に眺めたい

注意点:

- 取り込み方や強制的な操作など、影響の大きいボタンは特に慎重に
- 分からない操作は押さず、[リモートと GitHub](./remote) や [戻り方](./recovery) に戻って意味を確認する

## VS Code / Cursor の Git パネル

エディタ左側（またはソース管理ビュー）から、変更ファイルの確認、ステージ、コミット、ときどき push / pull ができます。  
コードを書きながら、同じ画面で Git 操作まで完結しやすいのが利点です。

向いている場面:

- 編集とコミットを短いサイクルで回したい
- ファイル単位のステージを、クリックで選びたい

注意点:

- 「全部コミット」系の操作は、意図しないファイルが混ざりやすい
- メッセージを空のまま進めてしまわない
- コンフリクトや複雑な履歴操作は、パネルだけで完結しないこともある

## この教材でのすすめ方

1. まずは [最初のコミットまで](./setup-and-first-commit) と [日常の操作](./daily-commands) で、コマンドの意味を一通り触る
2. その対応関係が頭に入ってから、GitHub Desktop やエディタの Git パネルを使う
3. 困ったら GUI の文言だけを追わず、`git status` など既知のコマンドで現在地を確認する

GUI は敵ではありません。しかし、その一方で万能ツールでもありません。  
**意味が分かったうえでの時短道具** として使うと、いちばんうまくいきます。

## まとめ

- 初心者にとって GUI は入りやすいが、GUI だけに頼ると履歴とトラブル対応が弱くなりやすい
- コマンドの概念を理解してから GUI に移る
- 画面の操作は、status / add / commit / branch / push・pull に対応づけて読む
