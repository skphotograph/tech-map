# つまずいたときの戻り方

「消したつもりが消えていない」「戻したいのに、戻し方が分からない」。  
Git で一番焦るのは、だいたいこのあたりです。  
ここでいきなり強いコマンドに手を出すと、共有済みの履歴まで巻き込むことがあります。  
このページでは、よくある「しまった」への対処を、**安全側から** 整理します。  
[日常の操作](./daily-commands) と [リモートと GitHub](./remote) を読んでいると分かりやすいです。

:::tip[最初の判断基準]

共有前なら戻しやすい。  
共有後（すでに push 済み）は慎重に。  
この区別が付くだけで、取りうる手段がかなり絞れます。

:::

## このページで分かること

- いまの変更を捨てる・退避する・コミット前に戻す、の使い分け
- まだ push していないコミットへの対処の考え方
- やってはいけない強制上書きの理由

## まず冷静に：今どこにいるか

```bash
git status
git branch
git log --oneline -n 5
```

次を区別できると、対処を選びやすくなります。

- まだステージもコミットもしていない変更か
- ステージまではしたか
- コミットしたが、まだ push していないか
- すでにリモートへ push 済みか

## ケース 1: 作業中の変更をいったん退避したい

本線のホットフィックス対応など、「いまの作業を残したまま別作業へ移りたい」とき。

```bash
git stash push -m "見出し作業の途中"
```

例:

```text
Saved working directory and index state On feature/heading-copy: 見出し作業の途中
```

いまの変更を棚に上げて、作業ツリーをきれいにした、という意味です。

戻すとき:

```bash
git stash list
```

例:

```text
stash@{0}: On feature/heading-copy: 見出し作業の途中
```

`stash@{0}` が一番新しい退避です。  
取り出すときは次です。

```bash
git stash pop
```

例:

```text
On branch feature/heading-copy
Changes not staged for commit:
      modified:   README.md
Dropped refs/stash@{0} (...)
```

変更が戻り、その stash がリストから外れた、という意味です。  
うれしい点は、コミットしなくても作業を棚卸しできることです。  
ただし stash を忘れやすいので、長く置くならブランチにコミットする方が安心なこともあります。

## ケース 2: ステージに乗せすぎた（まだコミット前）

```bash
# ファイルをステージから外す（ファイル自体は消えない）
git restore --staged README.md
```

成功時は通常メッセージが出ません。  
`git status` で、そのファイルが `Changes to be committed` から外れていれば OK です。

古い Git では `git reset HEAD README.md` も同趣旨で使われます。  
「ステージを外す」だけで、編集内容まで消えるわけではない点を押さえてください。

## ケース 3: 作業ツリーの変更を捨てたい（注意）

まだコミットしていない変更を、最後のコミットの状態へ戻します。

```bash
git restore README.md
```

成功時は通常メッセージが出ません。  
`git status` で変更が消えていれば、作業ツリー側は戻っています。

:::warning[破棄は取り消せない]

保存していない内容や、戻す対象を誤ると復元できません。  
捨ててよいと確信できるときだけ使います。  
迷ったらコピーを取るか、`stash` を先に。

:::

<details>
<summary>`git checkout -- ファイル` との関係</summary>

昔は `git checkout -- README.md` で同様の破棄をしていました。  
最近は意図が分かりやすい `git restore` が推奨される場面が増えています。

</details>

## ケース 4: 直前のコミットメッセージだけ直したい

まだそのコミットを push していないとき。

```bash
git commit --amend -m "見出しの説明文を分かりやすくする"
```

`--amend` は「直前のコミットを作り直す」操作です。

:::warning[共有後の amend は危険]

すでに push したコミットを amend して再度 push すると、履歴が食い違い、強制 push が必要になりがちです。  
共有後は原則使わない方が安全です。

:::

## ケース 5: 直前のコミット自体をなかったことにしたい（共有前）

```bash
# コミットを取り消すが、変更は作業ツリーに残す
git reset --soft HEAD~1
```

- `HEAD~1` … いまの先端から 1 つ前
- `--soft` … 変更内容は残る（やり直しやすい）

```bash
# コミットもステージも戻し、変更は作業ツリーに残す
git reset --mixed HEAD~1
```

`--hard` は変更そのものも消すため、破壊的です。  
使うなら十分理解してから。

<details>
<summary>`--hard` を安易に使わない</summary>

```bash
git reset --hard HEAD~1
```

コミットだけでなく、関連する未コミット変更も消えることがあります。  
「消えてよい」と断言できるとき以外は使わないでください。  
共有済み履歴への `--hard` + 強制 push は、チーム事故の定番です。

</details>

## ケース 6: すでに push したあとに誤りに気づいた

基本方針は次です。

1. **打ち消すコミットを新しく足す**（revert）
2. どうしても履歴を書き換えたい場合は、チームのルールを確認したうえで行う

```bash
git revert COMMIT_ID
```

例:

```text
[main c0ffee1] Revert "壊れた変更を入れる"
 1 file changed, 1 insertion(+), 3 deletions(-)
```

新しいコミットが 1 つ増え、指定した変更が打ち消された、という意味です。  
`COMMIT_ID` は `git log --oneline` で見える短い ID に置き換えます。

:::tip[共有後の取り消し]

`revert` は「あのコミットの変更を打ち消す新しいコミットを作る」操作です。  
履歴を消さずに済むので、共有後はこちらが安全寄りです。

:::

## 強制 push が危険な理由

```bash
# 例: こういった操作（安易に実行しない）
git push --force
```

:::warning[リモートの履歴を上書きする]

強制 push は、リモートの枝を自分の履歴で上書きします。  
他の人がその枝を基に作業していると、相手のコミットが見えなくなったり、取り込みが地獄になります。

:::

原則:

- `main` などの共有本線では使わない
- 使う必要があるなら、対象ブランチ・影響範囲・代替手段を確認してから

## 困ったときの相談用チェックリスト

1. `git status` の結果をコピーする
2. 直近の `git log --oneline -n 5` を控える
3. もう push したかどうかを確認する
4. 「消したい」のか「退避したい」のか「打ち消したい」のかを言葉にする

チームに相談するときは、この 4 点があるだけで支援が一気に早くなります。

## まとめ

- まず `status` / `branch` / `log` で現在地を確認する
- 共有前と共有後で、取ってよい手段が変わる
- 破棄（`restore`）と強制上書き（`--force`）は特に慎重に
- 共有後の取り消しは `revert` を優先して考える

これで Git の導入編は一通りです。
