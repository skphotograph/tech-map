# 経路・NAT・ファイアウォール

VPN に入る前は、検証 DB の `10.2.8.41` へ一切届かない。  
入ったあと、`ping` は通るのにアプリはまだタイムアウトする。  
番号も名前も合っているのに届かないとき、残るのは **道** と **門** です。

このページでは、デフォルトゲートウェイ、NAT、ファイアウォールを、開発者が構成図を読むのに必要な範囲で扱います。  
機器の設定そのものは書きません。

## このページで分かること

- 自分の網の外へ出すときの次の hop（ゲートウェイ）
- NAT が「内側の番号のままでは世界と話せない」問題をどう扱うか
- ファイアウォールがポート単位で通す／捨てること
- VPN が「別の網に一時的に加わる」こと

## 経路: 次に渡す相手

自分のマシンは、世界中の IP の場所を知りません。  
知っているのは、だいたい次です。

- 同じ塊（同じ CIDR）の相手には、直接話せる
- それ以外は、**デフォルトゲートウェイ**（次に渡すルータ）へ渡す

```text
宛先 10.2.8.41  は 自分と同じ 10.2.8.0/24 → 直接
宛先 203.0.113.10 は それ以外           → ゲートウェイへ
```

Linux では `ip route` で、今の道順の要約を見られます。

```bash
ip route
```

例:

```text
default via 10.2.8.1 dev eth0
10.2.8.0/24 dev eth0 proto kernel scope link src 10.2.8.41
```

読み方のポイント:

- `10.2.8.0/24 ... eth0` … 同じ塊は、この口から直接
- `default via 10.2.8.1` … それ以外は `10.2.8.1` へ渡す

VPN に入ると、この表に「`10.2.0.0/16` は VPN の口へ」のような行が増えます。  
増えない、または別の default が勝っていると、名前は引けても荷物が社内へ向かいません。

`No route to host` や、すぐ失敗する接続は、この表の欠落を疑います。  
返事がいつまでも無いタイムアウトは、道はあるが途中の門が捨てている、側が多いです。

## NAT: 内側の番号で外へ出る

[IP アドレス](./ip-addresses) のとおり、プライベートアドレスはインターネットの一意な宛先になりません。  
それでも、オフィスの PC から `https://example.com` は開けます。  
途中で **NAT**（Network Address Translation）が、内側の番号を一時的に公開側の番号へ書き換えるからです。

```mermaid
flowchart LR
  pc["PC 192.168.1.20"]
  nat[NAT / ルータ]
  web["example.com の公開 IP"]
  pc -->|"内側の番号"| nat
  nat -->|"公開側の番号"| web
  web -->|"返事"| nat
  nat -->|"元の PC へ戻す"| pc
```

うれしい点は、多数の内側マシンが、少数の公開アドレスで外へ出られることです。  
開発者として効く注意は、向きです。

| 向き                        | 起きること                                       |
| --------------------------- | ------------------------------------------------ |
| 内側 → インターネット       | NAT があれば、多くの場合は出られる               |
| インターネット → 内側の番号 | 何もしなければ届かない。公開側の入り口設計が要る |

だから、自宅 PC の `192.168.1.20` をチケットに書いても、クラウド上のアプリからは届きません。  
逆に、クラウドの DB がプライベートだけを持っていると、ノート PC から直接 `psql` できません。  
届けるなら、VPN、踏み台、クラウドの接続サービス、一時的な公開（検証でも穴は最小に）、のいずれかです。

:::tip[「自分の IP を許可して」の意味]

許可ルールに書く番号は、**相手から見た送信元** です。  
NAT の後ろにいると、相手に見えるのはルータや NAT ゲートウェイの公開側です。  
自宅の `ip addr` の `192.168.` をクラウドの許可に書いても、一致しません。

:::

## ファイアウォール: 通す会話を選ぶ

**ファイアウォール**（クラウドではセキュリティグループや NSG と呼ばれることが多いです）は、次の組で通す／捨てるを決めます。

- 送信元の IP または範囲
- 宛先の IP または範囲
- ポートと約束（TCP 443 など）
- 向き（入ってくる／出て行く）

許可されていない通信は、多くの現場では **黙って破棄** されます。  
アプリから見ると timed out です。  
「門が拒否してくれればすぐ分かるのに」は、開発者の本音としてよく出ます。現実は捨てる側が多い、と覚えてください。

現場で事故になる設定は、次に偏ります。

- SSH（22）や RDP（3389）を `0.0.0.0/0` に開ける
- データベース（5432 など）を世界に開ける
- 検証で自分の IP だけ開け、その穴を本番構成へコピーする
- アプリは通したが、ヘルスチェック用の送信元を許可し忘れる

ホスト OS の `firewalld` や `iptables` と、クラウドの許可ルールが **直列** になることもあります。  
片方だけ開けても、もう片方が捨てます。  
「画面では開けたつもり」でも、層が二つある、と考えます。

:::warning[DB のポートを世界に開けない]

パスワードがあるから公開してよい、にはなりません。  
総当たりの対象になり、アプリの欠陥の被害範囲も一気に広がります。  
内側に置き、アプリや踏み台からだけ届ける、が基本です。

:::

クラウド製品での具体（VPC、サブネット、負荷分散）は [クラウドのネットワーク](../../cloud/fundamentals/networking) に譲ります。  
ここでは「許可は最小の送信元と、必要なポートだけ」が、どの画面でも同じ、と押さえてください。

## VPN: 別の網に加わる

**VPN** は、今いる場所から、社内やクラウドの内側へ、暗号化されたトンネルを張る仕組みです。  
効果のイメージは、「自分の PC が、一時的に向こうの LAN の一員になる」です。

入ると次が変わります。

- プライベート IP への経路が増える
- 名前解決のリゾルバが社内向けに切り替わることがある
- 許可ルールの「社内レンジ」に、自分の送信元が入る

入っていない状態で内側のホスト名を叩くと、公開 DNS が答えを返せない、または関係ない番号を返す、ことがあります。  
「VPN 切れてませんか」は、失礼な確認ではなく、層の一番下に近い確認です。

## よくあるつまずき

- 自分のプライベート IP を、クラウドの許可リストに書いて届かない
- クラウドの門は開けたが、OS のファイアウォールが残っている
- VPN 未接続のまま、内側 DNS と内側 IP を疑う
- ping だけ通る状態を「全部開いている」とみなす（ICMP と TCP は別許可になり得る）

## まとめ / 次に学ぶとよいこと

- 同じ塊以外はゲートウェイへ渡す。VPN はその表を書き換える
- NAT は内側からの外出を助け、内側への直接到達は保証しない
- ファイアウォールは送信元・宛先・ポートで通し、許可しない通信は捨てることが多い
- 許可は最小に。DB と管理ポートを世界に開けない
