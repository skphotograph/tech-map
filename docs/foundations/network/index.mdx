# ネットワークをはじめよう

手元では注文画面が開くのに、検証サーバへ上げた瞬間だけ真っ白になる。  
SQL もアプリのログも異常が無い。同僚に聞くと「名前が引けるか」「ポートは開いているか」と返ってくる。  
コードを疑う前に、**誰が・どの宛先へ・どの入り口で話しているか** を見るのが、この章の仕事です。

開発者の仕事はルータを設計することではありません。  
一方で、業務システムの不具合のかなりの割合は、「届かない」「名前が違うホストを指している」「待っているポートが違う」です。  
ここが読めると、自分で切り分けられ、インフラ担当と短い言葉で話せます。

## この章で分かること

- クライアントとサーバ、パケット、「つながった」が指すもの
- IP アドレス、CIDR、ポート、TCP / UDP
- DNS による名前解決
- 経路、NAT、ファイアウォールが「届く／届かない」を決める理由
- `ping` や `dig`、待ち受け確認など、調査の順番

## こんな場面で効く

検証 DB のホスト名を設定したのに、タイムアウトだけが返る。  
ブラウザでは開ける URL が、サーバ上のアプリからは開けない。  
「VPN に入ってから」と言われる意味が、ピンとこない。

ネットワークの見方が付くと、次が自分の仕事として回せます。

- **失敗の層を切り分ける**: 名前解決か、到達か、待っているプロセスか
- **構成図の線を読む**: 公開の入り口と、内側だけのデータベースを区別する
- **再現手順を短く伝える**: ホスト、ポート、自分の IP、エラー文面

:::tip[この章のゴール]

「繋がらない」を一つの呪文にせず、名前・宛先・ポート・許可・待ち受けのどれが欠けているかを説明できる状態を目指します。

:::

## 学習のロードマップ

コマンドの暗記より、**層を順番に疑う感覚** を先に積みます。

1. [ネットワークの考え方](./concepts) … クライアントとサーバ、層、この章の地図
2. [IP アドレス](./ip-addresses) … 宛先の番号、プライベートと公開、CIDR
3. [ポート](./ports) … 同じホストの中の入り口、待ち受け
4. [TCP と UDP](./tcp-and-udp) … 接続、拒否、タイムアウトの違い
5. [DNS](./dns) … 名前を番号へ変える
6. [経路・NAT・ファイアウォール](./path-nat-firewall) … 届く道と、途中の門
7. [調べ方](./inspect) … 名前解決・疎通・待ち受けの確認順
8. [ブラウザからサーバまで](./from-browser) … 一連の旅と、相談するときの型

[Linux / Shell](../linux/) と [リモートアクセス](../remote-access/) を先に読むと、サーバへ入って確認する操作がスムーズです。  
ブラウザや API の中身（メソッド、ステータス、ヘッダ）は、このあとの [HTTP](../http/) で扱います。

:::info[クラウドの仮想ネットワークとの役割分担]

VPC やセキュリティグループといった **クラウド製品の箱** は、[クラウドのネットワーク](../../cloud/fundamentals/networking) 側です。  
この章は、その箱の中でも外でも共通する「宛先・ポート・名前・許可」の言葉を先に揃えます。

:::
