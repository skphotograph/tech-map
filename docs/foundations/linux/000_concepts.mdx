# Linux とシェルの考え方

コマンドを暗記する前に、「いま話している相手は誰か」を整理します。  
ここが曖昧だと、エラーの意味も、GUI との役割分担もつかみにくいままです。

## このページで分かること

- Linux・ディストリビューション・シェル・端末の違い
- bash / zsh / fish の特徴と、この章の想定
- なぜ SE の仕事で Linux / シェルが前提になりやすいか
- この章で扱う範囲の地図

## なぜイメージが先か

画面のボタンだけで仕事が完結しているうちは、「OS の中で何が動いているか」を意識しなくても進められます。  
ところが障害調査やデプロイでは、突然サーバの黒い画面に放り込まれます。  
そこで出てくる用語が全部別物に聞こえると、調査が止まります。

例として、Web アプリ `task-board` が応答しないとします。  
ブラウザでは真っ白、監視では「プロセスが生きている」、ログはどこかにあるはず——。  
このとき必要なのは新しいフレームワークの知識より、「どこにログインし、どのプロセスを見、どのファイルを読むか」という OS 側の見方です。

## Linux とは何か

**Linux** は、広く使われている OS（オペレーティングシステム）のひとつです。  
厳密には「Linux カーネル」とその周辺の仕組みを指すことも多いですが、現場では「Linux が入ったサーバ／環境」くらいの意味で会話されることがほとんどです。

うれしい点（この教材の観点）:

- サーバ・クラウド・コンテナの標準的な土台になっている
- 同じ考え方の操作が、環境をまたいで通じやすい
- 文字ベースの操作（シェル）と相性がよく、自動化しやすい

### ディストリビューション

「Linux」と一口に言っても、実際に触るのは **ディストリビューション**（配布のまとまり）です。  
Ubuntu、Debian、Rocky Linux、Amazon Linux など、パッケージの入れ方や初期設定が違います。

:::info[最初に覚えること]

ディストリが違っても、この章の **パス・権限・プロセス・パイプ** の考え方はほぼ共通です。  
最初から各ディストリの差分を暗記する必要はありません。

:::

<details>
<summary>カーネルとユーザー空間（ざっくり）</summary>

カーネルは OS の中核で、ハードウェアやプロセスを管理します。  
私たちが普段打つコマンドの多くは、その上の「ユーザー空間」のプログラムです。  
障害の深い話ではこの区別が効きますが、導入では「Linux 環境の上でシェルが動いている」くらいで十分です。

</details>

## シェルと端末

言葉が混ざりやすいので、次の対応で押さえてください。

| 用語 | ざっくり言うと | 例 |
| --- | --- | --- |
| **端末（ターミナル）** | 文字の入出力をする「窓口」アプリ | Terminal、Windows Terminal、VS Code / Cursor の統合ターミナル |
| **シェル** | あなたが打った文字を解釈し、プログラムを起動する「通訳」 | bash、zsh、fish など |
| **コマンド** | シェルに頼む具体的な指示 | `ls`、`cd`、`grep` |

```mermaid
flowchart LR
  you[あなた]
  terminal[端末]
  shell[シェル]
  program[コマンドやプログラム]
  you --> terminal
  terminal --> shell
  shell --> program
```

端末は画面、シェルは通訳、コマンドは実際の作業、という分担です。

:::tip[この章の主役]

以後この章で「シェルで操作する」と言うとき、主に **bash 互換** の書き方を想定します。  
プロンプトに出てくる `$` の右側にコマンドを書いて Enter、が基本動作です。

:::

<details>
<summary>`$` と `#` の違い</summary>

多くの教材では、一般ユーザーのプロンプトを `$`、管理者（root）を `#` で示します。  
`#` のときは権限が強く、破壊的な操作の影響も大きくなります。  
表示の形は環境で違うので、記号そのものより「今どのユーザーか」を意識してください。

</details>

## よく聞くシェル：bash / zsh / fish

シェルにも種類があります。  
どれも「コマンドを受け取ってプログラムを起動する」役割は同じですが、対話時の快適さや、スクリプトの方言が違います。

| シェル | 特徴 | よくある場面 |
| --- | --- | --- |
| **bash** | 長年の標準。ドキュメント・サーバ・CI の例が最も多い。POSIX 寄りの書き方が通じやすい | Linux サーバのログインシェル、多くの教材・自動実行 |
| **zsh** | bash に近い文法で、補完やカスタマイズが強い。macOS の既定シェルでもある | 個人の開発用端末、チームのローカル環境 |
| **fish** | 対話が親切（サジェストや色分けが強い）。一方で bash 用スクリプトをそのままは動かせないことが多い | 個人の対話用。サーバの既定にはなりにくい |

```bash
echo "$SHELL"
```

例:

```text
/bin/bash
```

`SHELL` は、ログイン時に使うシェルのパスが入っている環境変数です。  
いま動いているシェルと違うこともあるので、気になるときは次も使えます。

```bash
ps -p $$
```

例:

```text
  PID TTY          TIME CMD
 1842 pts/0    00:00:00 bash
```

`$$` は「いまのシェルの PID」です。  
`CMD` 列が、実際に会話しているシェルの名前の目安になります。

:::info[学習と実務での選び方]

- **学ぶ・共有する・サーバで動かす** … まず bash（この章の想定）
- **自分の PC を快適にしたい** … zsh も十分あり（多くの操作はこの章のまま通じる）
- **fish を使う** … 対話は快適でも、スクリプトや手順書は bash 向けに書く場面が多い

日常の `cd` や `ls`、`grep` のような外部コマンドはシェルが違っても同じです。  
差が出やすいのは、補完の挙動・設定ファイルの場所・スクリプトの書き方です。

:::

<details>
<summary>設定ファイルの場所（ざっくり）</summary>

- bash … `~/.bashrc` や `~/.bash_profile`（環境で差あり）
- zsh … `~/.zshrc`
- fish … `~/.config/fish/config.fish` など

「設定を足したのに効かない」ときは、いまのシェルと読み込みファイルの組み合わせを疑います。  
くわしくは [環境変数と PATH](./environment) も参照してください。

</details>

## GUI との役割分担

ファイルマネージャやエディタの GUI は、見やすさでは勝ちます。  
一方で次のような場面では、シェルの方が早い・正確・再現しやすいです。

- 大量のログから条件に合う行だけ抜き出す
- 同じ手順をチームで共有・自動化する
- GUI のないサーバに入って調査する
- 「今なにが動いているか」をプロセス単位で確認する

[Git の GUI](../git/gui-clients) と同様で、**意味が分かったうえでの時短** が安全です。

## この章で扱わないこと（境界）

次は隣接テーマなので、必要になったら別章へ進みます。

- IP や DNS、ポートの考え方 … ネットワーク基礎（予定）
- SSH やファイル転送の手順 … [リモートアクセス](../remote-access/)
- HTTP の中身 … HTTP（予定）
- コンテナ固有の話 … DevOps / コンテナ
- ディストリごとのパッケージ管理の詳細 … 必要になった環境の公式手順を優先
