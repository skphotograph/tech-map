# API の実務

注文ボタンを押した直後に画面が固まり、利用者がもう一度押した。  
サーバには同じ注文が二件ある。  
メソッドもステータスも正しくても、**待ち時間** と **もう一度送ってよいか** と **誰がそのリクエストを送っているか** を決めていないと、業務が壊れます。

このページでは、一般開発者として設計レビューや障害対応で効く判断をまとめます。  
新しいプロトコルは出ません。これまで学んだ部品の使い方です。

## このページで分かること

- 通信エラーと HTTP エラーの分離
- タイムアウトと、POST の再試行
- CORS がブラウザ限定の制限であること
- キャッシュが GET を「古い成功」のままにする理由

## 失敗は三種類

外部の注文 API を呼ぶとき、失敗は少なくとも三つに分かれます。  
[Python の HTTP クライアント](../../languages/python/applications/http-clients) でも、同じ分け方を使います。

| 種類              | 見え方                     | 次の手の例                                         |
| ----------------- | -------------------------- | -------------------------------------------------- |
| 届く前            | タイムアウト、名前解決失敗 | 経路、門、相手の生死。すぐ同じ POST を繰り返さない |
| HTTP としての失敗 | 4xx / 5xx                  | 4xx は入力や権限。5xx は相手のログと、再試行方針   |
| 本文の業務失敗    | 2xx ではない番号が望ましい | 在庫不足なら利用者へ返す。自動再送しない           |

これを一つの `catch` で空データに変えると、監視も利用者へのメッセージも、全部「よく分からない失敗」になります。  
少なくとも、届く前と 404 と 500 は、ログ上で分けてください。

:::tip[ステータスが無い／ある]

番号が無い失敗を、500 のハンドリングに流さない。  
層が違うので、直す場所も違います。

:::

## タイムアウトを空にしない

待ち時間の上限が無い呼び出しは、相手が黙ったとき、自分のワーカーやスレッドを埋めます。  
埋められた側は、関係ない利用者まで止めて、障害を横へ広げます。

目安の考え方です。

- **接続** の上限は短め（門が捨てているときに長く待たない）
- **応答読み取り** の上限は、相手が返す想定時間と、自分の画面が待てる時間の短い方
- 画面の操作と、夜間バッチでは、別の値にしてよい

「遅い SQL」と「門が捨てている」は、どちらも時間切れに見えます。  
`-v` で `Connected` まで行くか、DB 側のクエリ時間が見えるか、で戻る章が変わります。

## 再試行は冪等な操作だけ

自動でもう一度送ってよいのは、[メソッド](./methods) で見た **冪等な操作** に限ります。  
GET の再取得、[QUERY](./methods) の再検索、冪等キー付きの PUT、は候補です。  
素の POST で注文を切る処理は、候補から外します。

タイムアウトは特に厄介です。  
相手は処理を完了したのに、返事だけが消えた、という状態があり得ます。  
こちらが「失敗した」と思って POST を再送すると、二件目ができます。

現場での安全側です。

- 作成は、クライアントが **冪等キー**（同じキーなら二件目を作らない）を付けるか、二度押しを画面で止める
- 429 や 503 の再試行は、待ち時間を空け、回数の上限を付ける
- 500 を無条件に再送しない。相手が部分的に成功しているかもしれない

## CORS はブラウザの門である

画面の JavaScript が、別のオリジン（スキーム・ホスト・ポートの組）の API を呼ぶと、ブラウザが **CORS**（Cross-Origin Resource Sharing）を検査します。  
サーバ間の `curl` や、バックエンド同士の呼び出しには、この検査はありません。

そのため、次が同時に成立します。

- サーバ上の `curl` は 200
- ブラウザの画面だけ失敗し、Console に CORS と出る

開発者がやりがちな誤りは、CORS をファイアウォールの穴だと思って 443 を世界に開けることです。  
CORS は **ブラウザが、読んだレスポンスを JavaScript に渡してよいか** の制限です。  
許可は、API 側が応答ヘッダ（`Access-Control-Allow-Origin` など）で示します。  
事前に OPTIONS が飛ぶ（プリフライト）ことがあります。メソッドやヘッダが単純でないときです。

:::info[curl で通るのに画面だけ失敗]

先にオリジンの違いと CORS、混合コンテンツ（http と https の混在）を疑います。  
許可ルールや DNS より、ブラウザ固有の門です。

:::

## キャッシュ: 古い成功が残る

GET の応答は、途中の CDN やブラウザが覚えてよい、とヘッダで示せます。  
`Cache-Control: max-age=60` なら、短い間は再取得しません。  
業務の注文一覧にこれを付けると、作った直後の画面が古い、が起きます。

| 向き                        | よく使う判断                                  |
| --------------------------- | --------------------------------------------- |
| 公開してよいマスタの参照    | 短いキャッシュが効くことがある                |
| 個人の注文、認証付き GET    | `Cache-Control: private` や `no-store` を検討 |
| POST / PUT / PATCH / DELETE | キャッシュしない想定が普通                    |

`304 Not Modified` は、「持っているコピーのままでよい」です。  
本文が空でも、前回の GET が生きている、という意味であり、削除成功の 204 とは違います。

開発中に「直したのに画面が変わらない」ときは、コードだけでなく、このヘッダとブラウザのキャッシュも疑います。

## 一般開発者として役割を果たすとき

業務システムの一員として、HTTP とネットワークで求められるのは、専門家の代替ではなく次です。

- 再現を、メソッド・URL・ステータス・主なヘッダで残す（秘密は伏せる）
- 届く前、4xx、5xx、業務失敗を混ぜない
- 作成の再試行と、GET の再取得を区別する
- 画面固有（CORS、Cookie、混合コンテンツ）と、サーバ間の失敗を区別する
- 公開の会話は HTTPS。トークンはクエリに置かない
- 構成図の線を、名前・ポート・門の言葉で説明できる

言語のクライアント実装、DTO、例外マッピングは、それぞれの章へ進みます。  
クラウドの入り口は [クラウドのネットワーク](../../cloud/fundamentals/networking) です。  
認証の詳細はセキュリティのカテゴリです。

## よくあるつまずき

- すべての失敗を同じ例外に包み、再試行可否が分からなくなる
- CORS をネットワーク障害として、門を広げる
- 認証付き GET を長くキャッシュし、他人の画面が残る
- タイムアウト後の POST を、監視の自動復旧で再送する

## まとめ / 次に学ぶとよいこと

- 失敗は、届く前・HTTP 番号・業務、の三層で扱う
- タイムアウトを空にせず、冪等でない POST を自動再送しない
- CORS はブラウザの門。キャッシュは GET の「今」をずらす

これで HTTP の入口は一通りです。  
[章の入口](./) に戻るか、言語の API 実装、[クラウド](../../cloud/)、[設計](../../architecture/) へ進むと、同じ言葉が構成とコードに載ります。
