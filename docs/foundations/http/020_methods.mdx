# メソッド

ブラウザのアドレス欄に注文作成の URL を貼ると、一覧は出るが注文は増えない。  
同じパスでも、**何をしたいか** が違います。  
その動詞が HTTP の **メソッド** です。

業務 API では、パスで資源を表し、メソッドで操作を表す、という使い方が広く共有されています。  
フレームワークの注釈より先に、この約束を揃えておくと、ログと仕様書が同じ言葉になります。

## このページで分かること

- よく使うメソッド（GET / POST / PUT / PATCH / DELETE）
- 安全（safe）と冪等（idempotent）
- QUERY（本文付きの検索。RFC 10008）
- ブラウザのアドレス欄が GET であること
- 仕様と実装がずれたときの事故

## 資源に対する動詞

REST 寄りの API では、`/orders/42` のようなパスが資源、メソッドが操作です。  
[Java の REST と DTO](../../languages/java/applications/rest-and-dto) でも同じ対応を使います。  
ここでの目的は、開発者がログの `GET /orders/42` を読んで意味を取ることです。

| メソッド   | よくある意味                     | たとえ           |
| ---------- | -------------------------------- | ---------------- |
| **GET**    | 取得する。変えない想定           | 閲覧する         |
| **POST**   | 作る、または「やって」と依頼する | 新しい伝票を切る |
| **PUT**    | 全体を、送った内容で置き換える   | 伝票を差し替える |
| **PATCH**  | 一部だけ変える                   | 欄を一箇所直す   |
| **DELETE** | 消す                             | 伝票を破棄する   |

実際の API は、この表どおりとは限りません。  
それでも、チームの規約がこの表に近いと、キャッシュや再試行の判断が楽になります。  
動詞をパスに埋め込む（`/createOrder`）より、資源とメソッドに分ける方が、後から読む人が迷いにくいです。

```text
GET    /orders          一覧
POST   /orders          作成
GET    /orders/42       一件取得
PUT    /orders/42       42 番を全体置き換え
PATCH  /orders/42       42 番の一部変更
DELETE /orders/42       42 番を削除
```

HEAD は GET と同じだが本文を返さない、OPTIONS は「何が許されるか」を尋ねる、といった仲間もあります。  
CORS の事前確認で OPTIONS が出ることは、[API の実務](./api-practice) で扱います。

## 安全と冪等

メソッドには、慣習として次の性質が期待されます。  
法律ではありませんが、インフラ（キャッシュ、リトライ）がこの期待の上に乗っています。

| 性質     | 意味                                     | 向くメソッドの例 |
| -------- | ---------------------------------------- | ---------------- |
| **安全** | 資源の状態を変えない                     | GET、HEAD        |
| **冪等** | 同じ依頼を何回やっても、結果の状態が同じ | GET、PUT、DELETE |

GET で注文を作ると、次が壊れます。

- ブラウザの再読み込みやプリフェッチが、注文を増やす
- 途中のキャッシュが「同じ GET だから」と古い成功を返す、または逆に副作用を隠す
- 障害時の自動再試行が、二重注文になる

POST は、一般に **冪等ではありません**。  
同じ「作成してください」を二回送ると、二件できる、が普通です。  
だから、タイムアウトのあとに無条件で POST を再送すると、利用者がボタンを連打したのと同じ事故になります。  
対策（冪等キーなど）は [API の実務](./api-practice) です。

PUT は「この内容で 42 番にして」なので、二回目は同じ状態に収束しやすいです。  
DELETE も「無い状態にする」なので、二回目は 404 になる実装と、200 のままの実装がありますが、資源が無いという結果は揃いやすいです。

:::warning[GET に副作用を載せない]

検索のつもりで GET に「この条件で承認する」を混ぜないでください。  
アドレス欄、履歴、プロキシ、監視のヘルスチェックが、意図せず実行します。

:::

## QUERY: 本文で条件を渡す検索

一覧の絞り込みが複雑になると、現場では次のどちらに寄りがちです。

- **GET** のクエリ文字列に、条件を全部載せる
- 検索なのに **POST** して、JSON の本文に条件を載せる

前者は、URL の長さ制限、ログや履歴への残存、複雑な入れ子を書きにくい、といった限界があります。  
後者は本文を使える一方、POST は冪等ではないので、タイムアウト後の再送やキャッシュの前提が崩れます。  
「取ってくるだけなのに POST」は、このページの表と食い違う、よくある妥協です。

**QUERY** は、その隙間を埋めるメソッドです。  
[RFC 10008](https://www.rfc-editor.org/rfc/rfc10008.html)（2026年6月、Standards Track）で、HTTP のメソッドとして登録されています。  
対象の資源の範囲で問い合わせを行い、条件は **本文** に載せます。  
上で見た **安全** かつ **冪等** なので、同じ QUERY をやり直しても、注文が二つできる、といった状態変化は依頼しません。

```text
QUERY /orders HTTP/1.1
Host: shop.example.com
Content-Type: application/json
Accept: application/json

{"status":"OPEN","minTotal":1000}
```

GET の `/orders?status=OPEN` と同じ「閲覧」側です。  
違うのは、条件が URL ではなく本文にあることです。  
作成の `POST /orders` とは別物です。

|                  | GET            | 検索に使う POST        | QUERY                          |
| ---------------- | -------------- | ---------------------- | ------------------------------ |
| 条件の置き場     | 主に URL       | 本文                   | 本文                           |
| 安全・冪等       | はい           | いいえ（POST のまま）  | はい                           |
| いまの業務 API   | 一覧の定番     | 条件が長い検索でよく見る | 仕様は揃った。相手が受けてから |

日常の第一候補は、まだ GET と POST です。  
QUERY を送っても、サーバや途中の入り口が知らなければ **405** や **501** になります。  
ログに `QUERY` が出たら「本文付きの検索」と読み、自分から新規に載せるなら、相手と中継が通すかを先に確認します。

:::info[アドレス欄では送れない]

ブラウザのアドレス欄は GET のままです。  
QUERY は `curl` や `fetch` のように、メソッドを明示できるクライアント向けです。  
ブラウザから別サイトの API へ送るときは、先に OPTIONS が飛ぶことがあります。

:::

<details>
<summary>仕様上はキャッシュできるが、まだ当てにしない</summary>

RFC では、QUERY の応答をキャッシュしてよく、キーには URL だけでなく **本文** も含みます。  
同じ条件なら取り直さなくてよい、という意図です。  
一方、ブラウザや多くの CDN は、まだ GET と同じようには QUERY を覚えません。  
「QUERY にしたから速くなる」は、今のところ保証ではありません。

サーバが受けられる形式は、応答の `Accept-Query` で示すことがあります。  
対応の有無は `OPTIONS` の `Allow` を見るか、実際に送って 405 かどうかを見ます。

</details>

## ブラウザと API クライアントの差

アドレス欄に URL を貼って Enter を押すと、ブラウザは **GET** を送ります。  
フォームのボタンは、HTML の指定が無ければ GET、`method="post"` なら POST です。

そのため、次が起きます。

- 仕様書の POST を、アドレス欄で試して 405 や 404 になる
- GET で試せてしまう URL に、本来 POST の処理が実装されている
- JavaScript の `fetch` はメソッドを明示できるので、画面と `curl` で結果が違う

確認するときは、仕様と同じメソッドで送ります。  
「ブラウザで開けた」は GET の成功であり、作成 API の成功ではありません。

## 405 と、仕様のずれ

サーバが「そのパスはあるが、その動詞は受けない」とき、**405 Method Not Allowed** が使われます。  
404 は「その資源が無い（または見せない）」です。  
切り分けでは、パスを先に合わせ、次にメソッドを合わせます。

実装側のずれも事故になります。

- ドキュメントは PUT、実装は POST だけ
- 一覧は GET なのに、フィルタのたびに POST が必要
- QUERY を送って 405 になる（相手や中継が未対応）
- DELETE が実際には「削除フラグを立てる PATCH」で、二回目の意味が違う

チームでは、表の期待から外れるなら、仕様書に一行書く方が、推測で再試行するより安全です。

## よくあるつまずき

- アドレス欄の成功を、作成 API の確認だと思う
- GET に更新を載せ、キャッシュと再読み込みで副作用が出る
- 検索用 POST と QUERY を同じだと思い、作成の POST まで再送する
- PUT と PATCH を混同し、送っていない欄が消える（全体置き換え）
- タイムアウト後に POST を自動再送し、二重登録する

## まとめ / 次に学ぶとよいこと

- パスが資源、メソッドが操作、という読み方が API では共有されている
- GET は安全側。POST は冪等ではないことが多い
- QUERY は本文付きの検索（安全・冪等）。日常の第一候補はまだ GET / POST
- 確認は、仕様と同じメソッドで行う
