# ヘッダと本文

ステータスは 200。  
なのにクライアントは「JSON が読めない」と落ちる。  
本文は HTML のエラーページで、`Content-Type` は `text/html` でした。  
番号の次に読むのが、**ヘッダ**（付属情報）と **本文**（本体）です。

このページでは、種類の宣言、JSON、認証の印の置き場を扱います。  
暗号化そのものは次の [HTTPS](./https) です。

## このページで分かること

- よく使うリクエスト／レスポンスヘッダ
- `Content-Type` と `Accept`
- Cookie と Authorization の役割の違い
- 秘密をログと URL に残さない置き方

## ヘッダは「この文の取扱説明」

ヘッダは `名前: 値` の行です。  
本文が JSON でも HTML でも、先にヘッダを見てから開けます。

リクエスト側で特に見るもの:

| ヘッダ          | 役割                                     |
| --------------- | ---------------------------------------- |
| `Host`          | どのサイトとして扱ってほしいか           |
| `Accept`        | 返事に望む形式（例: `application/json`） |
| `Content-Type`  | 今送る本文の形式                         |
| `Authorization` | 身分の証明（Bearer トークンなど）        |
| `Cookie`        | ブラウザが自動で付ける印                 |
| `User-Agent`    | クライアントの名前。ログの手がかり       |

レスポンス側で特に見るもの:

| ヘッダ             | 役割                                     |
| ------------------ | ---------------------------------------- |
| `Content-Type`     | 本文の形式                               |
| `Set-Cookie`       | ブラウザへ印を預ける                     |
| `Cache-Control`    | キャッシュしてよいか（実務ページで再訪） |
| `Location`         | リダイレクト先や、作成した資源の URL     |
| `WWW-Authenticate` | 401 のとき、どんな証明が必要かの手がかり |

名前は大文字小文字を区別しない、と仕様上は扱われます。  
値の意味はヘッダごとに違います。  
自作ヘッダを増やす前に、既存の名前で足りないかを見てください。

## Content-Type と Accept

`Content-Type` は「**今の本文** が何か」、`Accept` は「**返事** に何が欲しいか」です。  
向きが逆なので、取り違えると 415 や、HTML を JSON として読む失敗になります。

```text
POST /orders HTTP/1.1
Host: shop.example.com
Content-Type: application/json
Accept: application/json

{"userId":"u-1","sku":"SKU-9","qty":2}
```

サーバは `Content-Type` を見て JSON として解き、`Accept` を見て JSON で返します。  
フォーム送信では `application/x-www-form-urlencoded` や `multipart/form-data` が来ます。  
API のつもりで JSON パーサだけを用意していると、画面フォームが突然 415 になります。

文字化けは、本文のバイト列と、宣言された charset の不一致で起きます。  
JSON では UTF-8 が実質の標準です。  
宣言と実体を揃えてください。

:::info[中身を見ずに型を決めない]

拡張子 `.json` でも、サーバが HTML を返すことはあります。  
必ず `Content-Type` と、ステータスをセットで見ます。

## JSON の本文

業務 API の本文は、JSON が多いです。  
オブジェクト（`{ }`）や配列（`[ ]`）で、名前と値の組を運びます。

```json
{
  "id": "42",
  "status": "OPEN",
  "total": 2400
}
```

押さえるのは次です。

- JSON として解けても、必要なキーがあるとは限らない
- 数字と文字列（`"42"` と `42`）は別物
- 日付の形式は API ごとに決める。推測でパースしない

巨大な本文を毎回ログの INFO に出すと、個人情報とトークンが残ります。  
調査用には、注文 ID とステータスなど、必要な項目だけにします。

## Cookie と Authorization

「ログインした人」を毎回載せる印は、大きく二つ出ます。

| 仕組み            | 誰が付けることが多いか     | 向く会話                    |
| ----------------- | -------------------------- | --------------------------- |
| **Cookie**        | ブラウザが自動             | 人が画面を使う Web          |
| **Authorization** | アプリやクライアントが明示 | サーバ間 API、モバイル、SPA |

Cookie は、サーバが `Set-Cookie` で預け、以降のリクエストにブラウザが `Cookie` を付けます。  
便利な一方、別サイトからのフォーム送信に付いてしまう、といった問題（CSRF）の土台にもなります。  
属性（`HttpOnly`、`Secure`、`SameSite`）の詳細はセキュリティの章へ譲り、ここでは「ブラウザが勝手に付ける印」と覚えてください。

Authorization は、例えば次の形です。

```text
Authorization: Bearer <token>
```

`<token>` はプレースホルダです。本物の値をサンプルやチケットに貼らないでください。  
サーバ間連携では、Cookie よりこちらの方が「誰が付けたか」が明確です。  
どちらも **ヘッダ** に置き、クエリやリポジトリには置きません。

:::warning[Authorization をログに出さない]

アクセスログのヘッダダンプ、障害票の `curl -v` 全文、チャットのスクリーンショットに、トークンが乗ります。  
共有する前に、値を伏せてください。

:::

## 本文が無いとき

GET や 204 では、本文が空です。  
[QUERY](./methods) は検索条件を本文に載せるので、この限りではありません。  
クライアントが「必ず JSON オブジェクトが来る」と決め打ちすると、削除成功で落ちます。  
ステータスが 204 ならパースしない、200 なら `Content-Type` を見てから読む、が安全です。

逆に、POST なのに本文が空で、全部クエリ、という API もあります。  
長さの制限とログ残存の理由で、更新は本文へ寄せる方が扱いやすいです。

## よくあるつまずき

- `Content-Type` を付けずに JSON を送り、サーバがフォームとして読む
- エラー時の HTML を JSON としてパースする
- トークンを URL に載せ、アクセスログへ残す
- Cookie 付きの画面用 API を、サーバ間から Authorization 無しで叩いて 401 になる

## まとめ / 次に学ぶとよいこと

- ヘッダは取扱説明、本文は本体。空行で区切る
- `Content-Type` は今の本文、`Accept` は欲しい返事
- 印は Cookie または Authorization。クエリとログには載せない
