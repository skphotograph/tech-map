# HTTP をはじめよう

画面のボタンを押すと、ブラウザは向こう側のプログラムへ文章を送り、返事を待ちます。  
その文章の約束が **HTTP** です。  
注文の作成、ログイン、ファイルの取得——業務システムの「外との会話」の大半は、この約束の上に乗っています。

[ネットワーク基礎](../network/) では、名前が引けて、ポートまで届くかを見ました。  
届いたあとに何を言い、何が返るかが、この章です。  
ここが弱いと、ステータス 200 なのに業務は失敗している、4xx と通信断を同じ「エラー」にまとめる、といった調査の迷子が起きます。

## この章で分かること

- リクエストとレスポンス、URL の読み方
- メソッドとステータスコードの意味
- ヘッダと本文、JSON、認証情報の置き場
- HTTPS（TLS）が守るものと、証明書の役割
- `curl` とブラウザの開発者ツールで会話を観察する方法
- タイムアウト、再試行、CORS、キャッシュなど、API 実務で効く判断

## こんな場面で効く

同じ URL なのに、ブラウザでは動き、サーバ間連携だけ失敗する。  
注文ボタンを二度押ししたら、同じ注文が二つできた。  
フロントの担当から「CORS で止まっている」と言われ、サーバのファイアウォールを疑ってしまう。

HTTP の読み方が付くと、次が一般開発者の仕事として回せます。

- **失敗の種類を分ける**: ネットワーク断、4xx、5xx、本文の業務エラー
- **API を再現する**: ブラウザやアプリの代わりに、同じリクエストを手元から送る
- **安全側の選択をする**: 秘密を URL に載せない、冪等でない処理を無闇に再送しない

:::tip[この章のゴール]

HTTP の一文（メソッド、URL、ステータス、主なヘッダ）を読んで意味を取り、業務 API の成功・失敗を層ごとに説明できる状態を目指します。

:::
