# ステータスコード

画面は「失敗しました」だけ。  
ログを開くと `200` と、本文の `"error":"在庫不足"` が並んでいる。  
HTTP としては成功扱いになり、監視もクライアントも、成功の経路を進みます。  
**番号** が約束とずれていると、本文が正しくても運用が壊れます。

ステータスコードは、レスポンス先頭の三桁です。  
このページでは、開発者が毎日使う番号と、クラス（種類）の読み方を揃えます。

## このページで分かること

- 1xx〜5xx のクラス
- 業務で頻出する番号の意味
- 401 と 403、502 と 504 などの近縁
- 本文で失敗を表し、番号だけ 200 にする弊害

## クラスで先に読む

細かい番号を全部暗記する前に、先頭の桁で層を分けます。

| クラス | 意味                         | 開発者の次の動き                   |
| ------ | ---------------------------- | ---------------------------------- |
| 1xx    | 途中経過                     | 普段は意識しなくてよい             |
| 2xx    | 成功                         | 本文を仕様どおり処理してよい       |
| 3xx    | 別の場所へ（リダイレクト等） | Location 先、キャッシュの再検証    |
| 4xx    | クライアント側の問題         | 送った内容、認証、権限、パスを疑う |
| 5xx    | サーバ側の問題               | サーバログ、依存先、過負荷を疑う   |

`curl` が `404` を返したとき、TCP も HTTP の会話も成立しています。  
[ネットワークの timed out](../network/tcp-and-udp) とは、すでに別の世界です。

:::tip[本文より先に桁]

JSON をパースする前に、クラスを見る。  
4xx なのに成功用の型へ流すと、エラー HTML やエラー JSON で落ちます。

:::

## よく使う 2xx / 3xx

| 番号    | 意味                           | 典型                               |
| ------- | ------------------------------ | ---------------------------------- |
| **200** | OK。成功。本文があることが多い | GET の取得                         |
| **201** | Created。作った                | POST の作成。Location で新しい URL |
| **204** | No Content。成功だが本文無し   | DELETE の成功実装の一つ            |
| **301** | 恒久的に移転                   | HTTP から HTTPS、パス正規化        |
| **302** | 一時的に別 URL へ              | ログイン後の画面遷移               |
| **304** | キャッシュのままでよい         | 条件付き GET がヒット              |

作成なのに 200 だけ返す API もあります。  
チームの規約に合わせつつ、**作成成功と取得成功をログで区別したい** なら 201 が読みやすいです。  
204 のあとに本文を期待するクライアントは、空をエラーと誤認します。仕様と実装を揃えてください。

リダイレクトは、ブラウザが自動で次の URL へ行きます。  
API クライアントは、勝手について行ってメソッドが GET に変わる、といった罠があります。  
POST のあと 302 を踏むと、意図しない GET 再送になることがあるので、作成 API の確認はリダイレクトを意識します。

## よく使う 4xx

| 番号    | 意味                                    | 疑うもの                                |
| ------- | --------------------------------------- | --------------------------------------- |
| **400** | Bad Request。要求が解けない             | JSON 破損、型、必須欠け                 |
| **401** | Unauthorized。誰かが分からない          | 未ログイン、トークン期限切れ、付け忘れ  |
| **403** | Forbidden。誰かは分かるが拒否           | 権限不足、IP 制限をアプリが表現した場合 |
| **404** | Not Found。対象が無い（または見せない） | パス、ID、削除済み、権限で隠す実装      |
| **405** | Method Not Allowed                      | GET で POST 専用を叩いた                |
| **409** | Conflict。今の状態と両立しない          | 重複作成、楽観ロック                    |
| **415** | Unsupported Media Type                  | Content-Type の不一致                   |
| **429** | Too Many Requests                       | レート制限。すぐ再送しない              |

401 と 403 は混同しやすいです。

- **401** … 身分の証明が無い／通らない。ログイン画面やトークン再取得が次
- **403** … 身分は通った。その操作は許可されていない

404 は、存在しない ID だけでなく、「この人には見せない」を 404 にする実装もあります。  
セキュリティ上の理由で、他人の資源を 403 ではなく 404 にする、という判断です。  
どちらにせよ、クライアントは「今の資格では取れない」と扱うことになります。

## よく使う 5xx

| 番号    | 意味                                  | 疑うもの                                     |
| ------- | ------------------------------------- | -------------------------------------------- |
| **500** | Internal Server Error。予期しない失敗 | 例外、想定外入力の未処理                     |
| **502** | Bad Gateway。上流が変                 | 負荷分散の後ろが落ちている、応答が壊れている |
| **503** | Service Unavailable。今は無理         | メンテ、過負荷、依存の停止                   |
| **504** | Gateway Timeout。上流が遅い           | 後ろのアプリや DB が時間内に返らない         |

502 / 504 は、利用者から見ると「API が死んだ」でも、実際は手前の入り口と、後ろのプロセスのあいだの失敗です。  
自分の PC から直接アプリのポートへ打てば 200、公開 URL だと 502、なら負荷分散と待ち受けの話に戻ります。

500 の本文にスタックトレースを載せると、調査は速いように見えて、内部経路やライブラリ版が外へ出ます。  
クライアントへは短いコードとメッセージ、詳細はサーバログ、が安全側です。  
Java 側の変換は [REST API と DTO](../../languages/java/applications/rest-and-dto) で扱っています。

## 200 と本文フラグだけにしない

次の形は、動いているように見えて、周りを壊します。

```text
HTTP/1.1 200 OK
Content-Type: application/json

{"success":false,"message":"在庫が足りません"}
```

起きる問題です。

- 監視が HTTP 200 を「生きている」と数える
- クライアントの `raise_for_status()` 相当が成功扱いになる
- リトライ実装が、業務失敗と通信成功を区別できない
- ブラウザの開発者ツールで、赤い行が付かず見逃す

業務失敗は 4xx（在庫不足なら 409 や 422 など、チームで決めた番号）、想定外は 5xx、が運用と揃いやすいです。  
どうしても本文フラグが必要なレガシー連携でも、**新規の API の第一候補にはしない**、と決めておくと事故が減ります。

## よくあるつまずき

- 4xx をサーバのバグとして起票し、送った JSON を見ない
- 401 のときに権限ロールだけを疑い、トークンの有無を見ない
- 502 をアプリの NullPointer と決め、負荷分散の後ろを見ない
- 成功番号のままエラー本文を返し、クライアントが成功経路でパースする

## まとめ / 次に学ぶとよいこと

- 先頭の桁で、成功・リダイレクト・クライアント・サーバを分ける
- 401 は身分、403 は権限、5xx の 502/504 は手前と後ろのあいだ
- 業務失敗を 200 に載せない
