# ファイルを運ぶ

リモート作業では、「ログインして編集する」以外に、**ファイルそのものを手元とサーバのあいだでコピーする** 場面が頻出します。  
ここでは SCP / SFTP を中心に、FTP の位置づけも整理します。

## このページで分かること

- `scp` でのファイル／ディレクトリコピー
- SFTP の考え方と使い分け
- FTP を避ける理由と、現場で残っているときの注意
- 転送前に確認したい安全ポイント

## SCP：単発コピーの定番

`scp` は、SSH を使ってファイルやディレクトリをコピーするコマンドです。  
使い勝手は `cp` に近く、接続先だけ `ユーザー@ホスト:パス` になります。

手元 → リモート:

```bash
scp ./notes/app.conf alex@203.0.113.10:/home/alex/app/
```

例（イメージ）:

```text
app.conf                                  100%  128    12.0KB/s   00:00
```

進捗とサイズが出れば、転送は進んでいます。  
リモート側のパスは、相手のファイルシステム上の場所です。

リモート → 手元:

```bash
scp alex@203.0.113.10:/var/log/app/error.log ./
```

ディレクトリごと送るときは `-r` です。

```bash
scp -r ./webroot alex@203.0.113.10:/home/alex/deploy/
```

ポートが 22 以外のとき:

```bash
scp -P 2222 ./notes/app.conf alex@203.0.113.10:/home/alex/app/
```

:::info[`-p` と `-P`]

`scp` ではポート指定が **大文字の `-P`** です。  
`ssh -p`（小文字）と混同しやすいので注意してください。

:::

## SFTP：対話的に運ぶ

SFTP は、SSH 上で動くファイル転送の仕組みです。  
GUI の SFTP クライアントを使う現場も多いですが、コマンドでも入れます。

```bash
sftp alex@203.0.113.10
```

`sftp` は、SFTP でリモートとファイルをやり取りするコマンドです。  
接続後は、おおよそ次のような操作感です。

```text
sftp> ls
sftp> put notes/app.conf
sftp> get error.log
sftp> bye
```

- `put` … 手元 → リモート
- `get` … リモート → 手元
- `ls` / `cd` … リモート側の操作（実装で差あり）
- `bye` または `exit` … 終了

:::tip[使い分け]

- 一発でパスが決まっている … `scp` が速い
- 相手のディレクトリを見ながら選ぶ … SFTP（GUI 含む）が向く

どちらも土台は SSH なので、鍵やユーザーの考え方は [SSH](./ssh) と同じです。

:::

## FTP：残っているものとして知る

FTP クライアントの例（環境に入っている場合）:

```bash
ftp 203.0.113.10
```

`ftp` は、FTP でファイル転送するための伝統的なコマンドです。  
ログイン後に `get` / `put` する、という流れ自体は SFTP に似て見えることがあります。

ただし [考え方](./concepts) で触れたとおり、**暗号化されない通信になりやすい** のが大きな問題です。  
パスワードやファイル内容が経路上で見えやすい形態が残っています。

:::warning[FTP を使う前に確認]

- 本当に FTP 以外が不可か
- VPN 内など、経路が保護されている前提か
- FTPS（TLS 付き）や SFTP への移行が検討されていないか

新規の「とりあえず FTP」は避け、チームの標準手段に従ってください。

:::

<details>
<summary>rsync という選択肢（入口）</summary>

`rsync` は、差分を見ながら効率よくコピー・同期するコマンドです。  
SSH 経由で使うことも多く、デプロイやバックアップの定番です。

```bash
rsync -av -e ssh ./webroot/ alex@203.0.113.10:/home/alex/deploy/webroot/
```

強力なので、削除同期（`--delete`）などは十分理解してから使います。  
まずは `scp` / SFTP で「運ぶ」感覚を固めてからで十分です。

</details>

## 転送前の安全チェック

- 宛先パスを間違えていないか（本番ディレクトリへ直接上書きしていないか）
- 秘密情報（鍵、`.env`、認証情報）を不要な場所へ置いていないか
- 転送後の権限は適切か（[権限](../linux/permissions)）
- 大きなファイルは、先にディスク空きを確認（[実務での使い方](../linux/daily-ops)）

:::tip[迷ったらコピー先をホーム配下に]

最初は `/home/自分/...` など、影響の小さい場所へ置き、配置手順が固まってから本番パスへ移す方が安全です。

:::

## よくあるつまずき

| 症状 | よくある原因 | 方向性 |
| --- | --- | --- |
| `Permission denied` | リモート側の書き込み権限不足 | 宛先ディレクトリの権限・所有者 |
| パスが無い | リモート側に親ディレクトリが無い | 先に SSH で `mkdir` |
| `scp` のポート指定が効かない | `-p` と `-P` の取り違え | `scp` は `-P` |
| FTP だけ失敗する | FW や受動モードの問題 | 可能なら SFTP へ。残りは環境担当と確認 |

## まとめ

- ファイル転送の第一候補は SCP / SFTP（SSH ベース）
- `scp` は単発、`sftp` は対話・GUI 向き
- FTP はレガシー。理由と経路を確認できるとき以外は使わない

これでリモートアクセスの入口は一通りです。  
[章の入口](./) に戻るか、続けてネットワーク基礎・HTTP へ進むと、つながりの全体像が見えやすくなります。
