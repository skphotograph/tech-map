# メッセージングをはじめよう

この章では、システム同士が **メッセージ** で仕事を渡す仕組みを学びます。  
手を動かす例は **Apache Kafka**、クラウド側の対応関係は **Google Cloud Pub/Sub** で示します。  
保存は RDB、短いコピーは Redis、という前の章のあと、「変更をほかの処理へ届ける」役割を切り出します。

## この章で分かること

- 同期の HTTP 呼び出しだけでは苦しくなる場面
- キュー（一件を一人が処理）と Pub/Sub（同じ知らせを複数がそれぞれ処理）
- Kafka のトピック、プロデューサ、コンシューマ、コンシューマグループ
- 少なくとも一度届くことと、二重処理への備え
- Cloud Pub/Sub のトピックとサブスクリプションの対応

## こんな場面で効く

注文の保存はできた。そのあとメールを送り、倉庫に知らせ、集計にも渡したい。  
これを注文 API の中で全部やると、メールサービスの遅延が画面の待ち時間になり、倉庫が止まると注文ボタンまで止まる。

朝出社したら、夜間に止まっていた倉庫システムへ、止まっている間の注文をまとめて流したい。  
表を数秒おきに「新しい支払い済みは無いか」と見に行くと、見る側が増えるたびにデータベースが忙しくなる。

メッセージングは、**保存した事実を、関係する処理へ後から届ける** ための仲介です。  
注文の正はこれまでどおり RDB に置き、知らせ方だけを分けます。

:::tip[この章のゴール]

「誰が書くか」「誰が読むか」「同じ知らせを何系統が読むか」を説明でき、Kafka で一行送り一行受け取り、Cloud Pub/Sub の用語に対応づけられる状態を目指します。

:::
