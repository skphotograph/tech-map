# インデックスと実行計画

データ件数が増えると、同じ `WHERE` でも急に遅くなります。  
**インデックス** は、表を先頭から全部読まずに済ませるための近道です。  
作りすぎも遅くするので、「何の条件で探すか」に合わせて付けます。

## このページで分かること

- インデックスが効く場面と、効きにくい条件
- `CREATE INDEX` の基本
- `EXPLAIN` で実行計画を読む入口

## インデックスとは何か

本の巻末索引に近いイメージです。  
`order_id` で探すことが多いなら、その列の索引があると、全行スキャンより速く目的の行へ辿れます。

```sql
CREATE INDEX idx_orders_user_id ON orders (user_id);
```

主キーや `UNIQUE` 制約を付けると、対応するインデックスも作られることが多いです。  
追加で付けるのは、「検索・結合・並び替えでよく使う列」が中心です。

うれしい点:

- `WHERE user_id = 10` や `JOIN ... ON o.user_id = u.user_id` が速くなりやすい

代償:

- `INSERT` / `UPDATE` / `DELETE` のたびに索引も更新するため、書き込みが重くなりうる
- 使われないインデックスは、容量と保守コストだけ増える

:::tip[先に遅い問い合わせを知る]

「一応全部にインデックス」は避けます。  
遅い SQL を特定し、その `WHERE` / `JOIN` / `ORDER BY` に効くかを見ます。

:::

## 効きやすい条件・効きにくい条件

効きやすい例:

- `WHERE user_id = 10`
- `WHERE status = 'paid' AND user_id = 10`（左側の列がインデックスと合う場合）
- 外部キー列での JOIN

効きにくい・注意が必要な例:

- `WHERE user_name LIKE '%hana%'`（先頭が曖昧）
- 列に関数をかけた条件（`WHERE LOWER(email) = ...`）で、そのままの列インデックスと噛み合わない
- ほぼ全行が当たる条件（選択性が極端に低い）

<details>
<summary>複合インデックスの順番</summary>

`(user_id, status)` のインデックスは、`user_id` 単体や `user_id + status` の条件には使いやすい一方、`status` だけには使いにくいことがあります。  
よく使う条件の左から並べる、が目安です。

</details>

## EXPLAIN で実行計画を見る

PostgreSQL では、実際に結果を返さず計画だけ見るときは `EXPLAIN`、実際に走らせて計測するときは `EXPLAIN ANALYZE` を使います。

```sql
EXPLAIN
SELECT order_id, amount
  FROM orders
 WHERE user_id = 10;
```

出力例（環境で変わります）:

```text
Index Scan using idx_orders_user_id on orders
  Index Cond: (user_id = 10)
```

別の例では、次のように出ることもあります。

```text
Seq Scan on orders
  Filter: (user_id = 10)
```

| 見え方の例        | ざっくり言うと                     |
| ----------------- | ---------------------------------- |
| `Seq Scan`        | 表を順に読む（全件スキャンに近い） |
| `Index Scan` など | インデックスを使って候補へ辿る     |

:::info[計画は件数が変わると変わる]

同じ SQL でも、統計情報や件数によって計画が変わります。  
「昨日は速かった」は、データ量の変化でも起きます。

:::

`EXPLAIN ANALYZE` は実際に実行します。  
更新系に付けて試すときは、トランザクションで囲んで `ROLLBACK` するなどの安全策を取ります。

## 付け方の実務的な順序

1. 遅い問い合わせを特定する（アプリログや `slow query` 相当）
2. `EXPLAIN` / `EXPLAIN ANALYZE` で、全件スキャンや想定外の行数になっていないか見る
3. 条件列・結合列にインデックスが無いか確認する
4. 追加したら、書き込み負荷と効果の両方を見る

アプリ側の N+1（ループ内で都度 SQL）は、インデックスだけでは解消しません。  
発行回数そのものを減らす設計もセットで見ます。

## よくあるつまずき

- 遅い原因がネットワークやアプリの N+1 なのに、インデックスだけ増やす
- 先頭 `%` の `LIKE` に通常の B-tree インデックスを期待する
- 本番でいきなり `EXPLAIN ANALYZE` 付きの重い更新を流す

## まとめ

- インデックスは条件検索や結合を速くするための近道である
- 書き込みコストとのバランスを見て、遅い問い合わせに合わせて付ける
- `EXPLAIN` で Seq Scan か Index Scan かなど、計画の入口を読めるようにする

これで SQL / RDB の基礎ルートは一通りです。  
Java から接続するなら [JDBC の基礎](../../languages/java/basics/jdbc-basics) へ進み、データの置き場所の選択肢を広げるなら [データ](../) の NoSQL・メッセージングへ進みます。
