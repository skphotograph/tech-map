# Entra ID と RBAC

サブスクリプションの Owner を開発者全員に付けると、誰でもグループごと削除できます。  
Azure の人間の身分は **Microsoft Entra ID**（旧称 Azure AD）です。資源への許可は **RBAC**（ロールベースのアクセス制御）です。  
アプリは接続文字列の秘密キーより、**マネージド ID** を実行環境に付けます。

## このページで分かること

- スコープ（管理グループ / サブスクリプション / リソースグループ / 資源）
- 組み込みロールの広さ
- マネージド ID と、秘密を Git に置かないこと

## スコープとロール

RBAC は「このプリンシパルに、このスコープで、このロール」です。  
同じ Reader でも、サブスクリプション全体か、`rg-shop-dev` だけかで被害範囲が違います。

よく見る組み込みロールです。

| ロール                        | イメージ                          |
| ----------------------------- | --------------------------------- |
| Reader                        | 見る                              |
| Contributor                   | 資源は作れるが、RBAC は付けにくい |
| Owner                         | 権限の付与も含む                  |
| Storage Blob Data Contributor | そのストレージの Blob を読み書き  |

Contributor でも VM や DB は作れます。日常の「デプロイ担当」に Owner は広すぎます。  
検証グループに Contributor、本番はより狭いロール、が方向です。

割り当てを見る例:

```bash
az role assignment list --resource-group rg-shop-dev --output table
```

成功時は、プリンシパルとロール名が表で出ます。  
自分の作業用アカウントが Owner になっていないかを、ここで確認できます。

## マネージド ID

App Service や VM に **システム割り当てマネージド ID** を付けると、Entra ID 上の身分が実行環境に生まれます。  
その ID に、Blob の Data Contributor を **ストレージアカウントのスコープ** で付けます。  
接続文字列にアカウントキーを直書きしなくてよくなります。

ローカル検証でキーが必要なときも、App の設定や Key Vault に置き、リポジトリにはプレースホルダだけを残します。

:::warning[アカウントキーをソースに置かない]

ストレージアカウントのアクセスキーは、漏れると中身の読み書きが通ることがあります。  
回転（再発行）したら、古いキーを使っていた場所が全部 403 になります。  
マネージド ID を先に使い、キーは緊急用に近い位置づけにします。

:::

旧ドキュメントの「Azure AD」は、いまの Entra ID です。  
画面の名前が混ざっていても、人間のディレクトリと、RBAC の割り当て、という二層は同じです。

## よくあるつまずき

- ポータルの自分と、App Service のマネージド ID が別なのに、同じ権限だと思う
- サブスクリプション Owner を「とりあえず」付け、後から外せない政治になる
- Key Vault のアクセスポリシーと RBAC が混在し、どちらが効いているか分からない

## まとめ

- Entra ID が人間とアプリのディレクトリ、RBAC はスコープ付きの許可である
- Owner を日常に使わず、グループや資源の狭いロールにする
- マネージド ID を先に使い、アカウントキーを Git に置かない
