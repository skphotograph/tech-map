# クラウドとは何か

金曜の午後、注文 API の改修はマージ済みです。  
動かす箱が無い、とインフラ担当から「サーバは来週届く」と返ってくると、コードの完成とリリースの間に空白ができます。  
クラウドは、この空白を「必要な計算や保存を、画面と API から借りる」に変えた仕組みです。

## このページで分かること

- クラウドが指すもの（機器を買わず、ネットワーク越しに資源を使う）
- 速くなる部分と、設計・運用として残る部分
- 開発者が現場で聞かれるようになる判断

## 借りて使う計算資源

**クラウド** とは、事業者のデータセンターにある計算・保存・ネットワークを、インターネット経由の API やコンソールから利用する使い方です。  
自分たちでラックを購入し、電源と空調を用意し、機器が届くのを待つ、という手順を、多くの場合は経由しません。

うれしい点は、次に集約できます。

- **用意が速い**: 検証用のデータベースを、申請から数週間待たずに起動できる
- **必要な分だけ**: キャンペーン期間だけアプリの台数を増やす、といった伸縮がしやすい
- **運用の一部を任せられる**: ディスク故障の交換作業そのものは、事業者が引き受けることが多い

「誰かのコンピュータを借りている」は比喩として半分正しく、半分足りません。  
中身は本物のコンピュータとネットワークです。  
違うのは、**自分たちが物理機器の所有者にならなくても、API で同じ種類の部品を組み立てられる** ことです。

```text
従来（イメージ）          クラウド
購入 → 搬入 → 配線        コンソール / CLI / API
OS 導入 → アプリ配置      同じ「配置」は残る
故障したら交換待ち        機器交換は事業者側、設計ミスは自分たち
```

## 開発者の役割はどう変わるか

アプリのコードを書く仕事は残り続けます。  
変わるのは、次のような会話に開発者が入ることです。

- この API は、仮想マシンに載せるのか、ソースやコンテナを渡す基盤に載せるのか
- 商品画像はアプリのディスクに置くのか、オブジェクトストレージに置くのか
- データベースは、世界から届く公開アドレスを持ってよいのか
- 検証用の権限を、本番と同じアカウントで使っていないか

これらは「インフラ担当だけの話」に見えやすいですが、環境変数、接続先、ログの場所、公開範囲は、アプリの動きに直結します。  
障害の夜に「アプリは生きているのに DB に繋がらない」と切り分けるとき、クラウドの部品名が読めるかどうかで速度が変わります。

:::info[クラウドに移しても消えないもの]

スキーマ設計、トランザクション、入力チェック、秘密情報の扱い、テストは、クラウドの有無で不要になりません。  
速くなるのは箱の用意であり、業務ルールの正しさの責任は残ります。

:::

## このカテゴリの題材

通販風の **注文 API**（`shop-api`）を、このカテゴリの共通の例にします。

- 注文の正はリレーショナルデータベースへ残す
- 商品画像や請求書 PDF は、サーバのディスクとは別に、名前（キー）で置く倉庫（**オブジェクトストレージ**）へ置く
- 利用者は HTTPS でアプリに届く

GCP、AWS、Azure は、この同じ形を別の商品名で提供します。  
この章では部品の役割を固定し、各事業者の画面と CLI は GCP / AWS / Azure の章で操作します。

## よくあるつまずき

- 「クラウドに置けば落ちない」と思い、バックアップや障害時の手順を設計しない
- 画面から作れることと、作ってよいことを混同する（検証の強い権限、公開バケット）
- 事業者の障害と、自分たちの設定ミスを切り分けずに、全部を「クラウドが悪い」とまとめる

## まとめ

- クラウドは、計算・保存・ネットワークを API 経由で借りる使い方である
- 速いのは用意であり、設計と公開範囲と料金の責任は残る
- 開発者は、接続先・権限・ログを、構成図の言葉で話せるようになる
