# アカウントと IAM

検証用に付けた「何でもできる権限」を、本番のデプロイにも使い続けると、漏れた瞬間の被害が最大になります。  
クラウドでは、仮想マシンやバケットより先に、**誰の身分で操作しているか** が事故の大きさを決めます。  
この仕組みをまとめて IAM（Identity and Access Management、身分とアクセスの管理）と呼びます。

## このページで分かること

- 組織・請求・プロジェクト（アカウント）の入れ子
- 人間のログインと、アプリの身分の違い
- 最小権限と、長期の鍵をコードに置かない理由

## 入れ子の単位

事業者ごとに名前は違いますが、入れ子の感覚は近いです。

| 層           | ざっくり言うと                           | 現場での失敗例                           |
| ------------ | ---------------------------------------- | ---------------------------------------- |
| 組織         | 会社や部門の一番外側                     | 個人の無料アカウントの上に本番を建てる   |
| 請求         | 誰の支払い方法に乗るか                   | 検証と本番の請求が混ざり、内訳が追えない |
| プロジェクト | 資源をまとめる箱（AWS ではアカウント等） | 検証操作が本番の箱の中で行われる         |

GCP は **プロジェクト**、AWS は **アカウント**、Azure は **サブスクリプション** と **リソースグループ** が、日常の「今どの箱に作っているか」になります。  
ログインした人と、今選んでいる箱と、請求先は別物になり得ます。

:::tip[作業前に確認する]

いまの操作は、どの箱に対するものか。  
検証のつもりが本番の箱になっていないか。  
この二点が、権限の細かい文法より先に効きます。

:::

## 人間とアプリの身分

操作する主体は、大きく二つです。

| 主体                 | 例                                        | 向く使い方                       |
| -------------------- | ----------------------------------------- | -------------------------------- |
| 人間                 | 社員のログイン                            | コンソール、手元の CLI、レビュー |
| アプリやバッチの身分 | サービスアカウント、ロール、マネージド ID | 実行中の API がストレージへ書く  |

人間の強い権限でアプリを動かすと、その人が退職した・トークンが漏れたときに、アプリも一緒に壊れます。  
逆に、アプリ用の身分に「組織の全削除」まで付けると、アプリの脆弱性がクラウド全体の事故になります。

**認証** は「誰か」を確かめること、**認可** は「その誰が、何をしてよいか」です。  
IAM の設定の大半は認可側です。ログインできることと、バケットを消してよいことは別です。

## ロールとポリシー

現場の会話では、次の言葉がよく出ます。

- **プリンシパル**: 操作する主体（人、アプリの身分、別システム）
- **ロール / ロール割り当て**: その主体に付ける「仕事のセット」
- **ポリシー**: 許可または拒否の文面（どの操作を、どの資源に）
- **資源**: バケット、仮想マシン、データベースインスタンスなど

「開発者ロール」を全員に付ける、は楽です。  
そのロールが本番の削除まで含むなら、楽さと事故の大きさがセットになります。  
**最小権限** は、今の仕事に必要な操作だけを付ける、という考え方です。最初から完璧にはできません。検証は広め、本番は狭い、という段階でも、方向は揃えます。

<details>
<summary>root や Owner を日常使いしない</summary>

AWS のルートユーザー、GCP のプロジェクト Owner、Azure のサブスクリプション Owner は、請求や権限の付与まで含むことが多く、強力すぎます。  
日常のデプロイや調査には、個人用の弱い身分を使い、強い操作は承認と短い時間に限る、が事故を小さくします。

</details>

## 鍵をリポジトリに置かない

アプリがクラウド資源を触るとき、昔の手順では「アクセスキーを環境変数ファイルに書いて Git に含める」が起きていました。  
リポジトリが漏れれば、その鍵の権限の範囲で、第三者の操作になります。

いまの基本は次です。

- 人間の操作: ログイン（可能なら多要素認証）
- アプリの操作: 実行環境に付いた身分（ロールやマネージド ID）を使い、長期キーを発行しない
- どうしてもキーが必要なとき: 秘密管理の仕組みに置き、Git とチケットとログから除外する。サンプルはプレースホルダにする

```text
# 教材や設定例で書いてよい形
DATABASE_URL=postgresql://appuser:secret@host:5432/appdb

# 実際の値は実行環境側。リポジトリには置かない
```

上の `secret` はプレースホルダです。本物のパスワードに置き換えて共有しないでください。

## よくあるつまずき

- 検証用の広い権限のまま、本番デプロイの設定を流用する
- コンソールでは正しい箱を見ているのに、CLI の現在プロジェクトが別の箱
- キーを無効化したあと、どこで使っていたかが分からず、アプリが突然 403 になる

## まとめ

- 組織・請求・資源の箱は別層で、今どの箱を触っているかを先に確認する
- 人間とアプリの身分を分け、認可は仕事に必要な範囲にする
- 長期の鍵を Git に置かず、実行環境の身分や秘密管理を使う
