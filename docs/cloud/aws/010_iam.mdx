# IAM

アプリの設定ファイルに `AWS_ACCESS_KEY_ID` を直書きし、そのキーが AdministratorAccess だと、Git の漏洩がアカウント乗っ取りに直結します。  
AWS の認可は **IAM** です。人間はユーザ（または Identity Center）、アプリは **ロール** を実行環境に付けます。

## このページで分かること

- ポリシーが許可する操作と、ロールの引き受け
- EC2 や ECS にロールを付ける理由
- アクセスキーをリポジトリに置かないこと

## ユーザ、グループ、ロール

| 種類     | ざっくり言うと                     | shop-api での例                 |
| -------- | ---------------------------------- | ------------------------------- |
| ユーザ   | 人間の長期身分（キーを持ち得る）   | 開発者のコンソールログイン      |
| グループ | ユーザのまとまりに同じポリシー     | 開発者グループに読み取り        |
| ロール   | 引き受けると一時的な資格になる身分 | EC2 / ECS タスクが S3 へ書く    |
| ポリシー | 許可または拒否する操作の文面       | `s3:PutObject` を特定バケットへ |

ポリシーは JSON で、`Action` と `Resource` を書きます。  
最初から文法を暗記する必要はありません。コンソールのシミュレータや、拒否された `Action` 名をログから拾う、が現場の入り方です。

AdministratorAccess を開発者全員に付けると、[最小権限](../fundamentals/iam-and-accounts) の逆です。  
検証でも、削除と IAM 変更は別ロールに分離できると、事故が小さくなります。

## アプリはロール

EC2 インスタンスプロファイル、ECS タスクロール、Lambda の実行ロールは、いずれも「この計算にこのロールを付ける」です。  
アプリは、環境変数の長期キーではなく、実行環境が配る **一時的な資格情報** を使います。  
鍵のローテーションを自分でファイル管理しなくてよく、漏れたファイルが永久に効く、という状態を避けられます。

ローカルから S3 を試すときだけ、自分のユーザのキーや、短いセッションを使います。  
そのキーをコンテナに焼き込んで本番へ出さないでください。

:::warning[アクセスキーを Git に置かない]

`AKIA` で始まる ID と秘密キーは、リポジトリ、チャット、チケット、アプリのログから除外します。  
誤ってコミットしたら、無効化が先です。履歴に残った前提で、権限の範囲を見直します。  
サンプルではプレースホルダだけを書きます。

:::

```text
# 書いてはいけない（例。本物を置かない）
AWS_ACCESS_KEY_ID=AKIA...
AWS_SECRET_ACCESS_KEY=...
```

## ARN

AWS では資源を **ARN**（Amazon Resource Name）で指します。

```text
arn:aws:s3:::shop-dev-images-123456
arn:aws:iam::123456789012:role/shop-api
```

ポリシーの `Resource` にこの形式が並びます。  
「どのバケットか」が `*` だと、意図しないバケットまで書けます。

## よくあるつまずき

- 拒否された操作名を見ず、AdministratorAccess を足して切り分けを終わらせる
- コンソール用ユーザと、CLI のアクセスキーのユーザが別で、片方だけ権限が足りない
- Identity Center と IAM ユーザが混在し、誰の操作か監査できない

## まとめ

- 人間はユーザまたは Identity Center、アプリはロールである
- ポリシーは Action と Resource、日常に AdministratorAccess を使わない
- アクセスキーは Git に置かず、実行環境のロールを使う
